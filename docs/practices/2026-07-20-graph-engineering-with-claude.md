## 요약

멀티스텝 에이전트를 만들면 대부분 직선이 나옴. 1단계, 2단계, 3단계가 앞 단계 끝나기를 얌전히 기다림. 근데 그중 절반은 애초에 기다릴 이유가 없었음. 이 글은 그 일렬 종대를 그래프로 다시 그리는 14단계임. Claude Code의 dynamic workflows를 전제로 쓰였고, 오케스트레이션이 대화가 아니라 코드라서 조율 자체엔 모델 토큰이 안 든다는 걸 지렛대로 씀.

## 핵심 전제

프롬프트는 문장이고 루프는 순환이고 하네스는 에이전트가 딛는 바닥임. 근데 작업 자체의 모양, 그러니까 무엇이 무엇보다 먼저 돌고 무엇이 동시에 돌 수 있고 무엇이 전부를 기다려야 하는지, **그 모양은 그래프임.** 노드가 생각하고 엣지가 결과를 나름.

## 01~04. 노드와 엣지 바로 세우기

**노드는 일, 엣지는 흐르는 것.** 노드는 에이전트 하나, 경계 분명한 일 하나, 입력 하나에 출력 하나. 엣지는 의존성이고, 이 노드의 출력이 저 노드의 입력으로 들어간다는 뜻임. 그게 전부.

흔한 실수가 "그리고 나서"를 엣지로 취급하는 것. "파일을 요약하고 나서 날씨를 알려줘"에는 둘 사이에 엣지가 없음. 날씨는 요약을 소비하지 않으니까. 자기 에이전트의 모든 "그리고 나서"에 물어봐야 함. 다음 단계가 앞 단계 출력을 읽는가? 아니면 엣지는 없고 그 대기는 낭비임.

**선형 스크립트는 퇴화한 그래프임.** A→B→C→D는 모든 노드가 들어오는 엣지 하나, 나가는 엣지 하나인 사슬임. 돌긴 돔. 느리고 취약할 뿐임. C가 멈추면 D는 영영 안 돌고 A의 작업은 갈 곳 없이 상류에 갇힘.

**노드마다 계약을 줌.** 추론할 수 없는 노드는 병렬화할 수 없는 노드임. 경계 있는 입력, 경계 있는 출력, 정확히 하나의 일. 워크플로에선 스키마로 강제함. `agent()` 호출에 JSON 스키마를 주면 서브에이전트가 검증된 구조화 데이터를 반환하도록 강제되고, 검증이 툴 호출 레이어에서 일어나니까 불일치 시 재시도함. 파싱하고 기도할 필요가 없음.

**엣지도 데이터 계약임.** "B가 A 다음"이 아니라 "A는 이 모양을 만들고 B는 이 모양을 소비한다"는 약속임. 순서가 아니라 데이터로 엣지에 이름을 붙이면 엣지가 진짜인지 즉시 보이고, 모양만 유지되면 양쪽 노드를 갈아끼울 수 있음. 팬아웃이랑 합성 사이의 reduce 단계, 즉 flatten·dedupe·filter는 그냥 코드임. 에이전트 필요 없음. 사람들이 모델 토큰 태우는 일의 상당수가 실은 엣지고, **엣지에는 모델 호출이 없으니 토큰 비용이 안 붙음.** (CPU·메모리·구현 비용은 당연히 듦)

## 05~07. 팬아웃, 팬인, 다이아몬드

**`parallel()`로 팬아웃.** 독립적인 노드가 N개면 체인하지 말고 한꺼번에 던짐. 두 가지 디테일이 이걸 견고하게 만듦. 첫째, `parallel()`은 배리어라서 모든 thunk를 기다린 뒤 반환함. 둘째, 예외를 던진 thunk는 배치 전체를 실패시키는 대신 null로 해소됨. 이건 이 워크플로 런타임의 계약이고 `Promise.all` 같은 일반 구현은 첫 예외에서 전체를 reject하니 옮겨 쓸 때 확인해야 함. 그러니 항상 `.filter(Boolean)`. 동시 실행은 코어 수 근처에서 제한되고 나머지는 큐에 들어가니까 백 개를 넘겨도 다 끝남.

여기가 진짜 이득 나는 지점임. 팬아웃이 모델 대화가 아니라 Claude가 쓴 코드 안에서 일어남. Claude의 컨텍스트는 소스 아홉 개를 동시에 안 들고 있음. 서브에이전트가 각자 자기 컨텍스트를 지고 최종 답만 돌려줌.

**배리어에서 팬인.** 팬아웃은 뭔가가 모아줘야 쓸모가 있음. 전체 집합이 있어야 하는 일, 그러니까 소스 간 중복 제거, 영향도 랭킹, 총계가 0이면 조기 종료 같은 걸 할 때만 배리어가 벽시계 비용을 정당화함.

판별법이 단순함. `parallel → transform → parallel`을 썼는데 가운데 transform에 항목 간 의존성이 없으면, pipeline을 썼어야 하고 배리어는 건너뛰었어야 함.

**다이아몬드.** 팬아웃이랑 팬인을 합치면 나오는 주력 토폴로지임. 한 노드가 쪼개고, 여러 노드가 병렬로 일하고, 한 노드가 합침. 정식 이름은 fan out → reduce → synthesize. 시장 조사, 의존성 감사, 코드 리뷰, 리서치 리포트 전부 이 골격임. 다이아몬드가 보이기 시작하면 "에이전트가 더 많은 단계를 하게 하려면"이 아니라 "쪼개는 곳은 어디고 합치는 곳은 어디인가"를 묻게 됨.

## 08~11. 라우팅, 검증, 격리, 순환

**런타임 조건부 라우팅.** 라우터 노드가 결과를 보고 어느 하류 경로를 태울지 정함. 워크플로에선 검증된 출력에 대한 JavaScript `if`나 `switch`일 뿐임. 판단은 Claude가 하고 라우팅은 Claude가 쓴 코드가 함. 같은 분류에 대해 매번 같게 돔. "Claude가 감사를 건너뛰기로 했다" 같은 창발적 사고가 없음. 건너뛰려면 그래프에 쓰여 있어야 하는데 안 쓰여 있으니까.

**엣지 위에 검증자.** 그래프의 진짜 레버리지는 에이전트 수가 아니라 그 주위에 두를 수 있는 구조임. 검증자 노드는 결과가 하류로 가기 전에 앉아서, 그 발견을 **죽이는 것만을** 임무로 삼음.

- 적대적 검증: 발견마다 반박하도록 프롬프트된 독립 회의론자 N명을 띄우고, 과반이 살아남을 때만 통과
- 관점 다양화 검증: 검증자마다 다른 렌즈를 줌. 정확성, 보안, 재현 여부. 동일한 검사 N개가 못 잡는 실패 모드를 다양성이 잡음
- 심사 패널: 서로 다른 각도로 N개 시도를 만들고 병렬 심사자로 채점한 뒤, 승자를 기반으로 합성하되 차점자의 좋은 부분을 접붙임

**격리.** 사슬에선 실패가 연쇄함. 그래프에선 노드에 갇혀야 함. `parallel()` 안에서 예외는 null이 되니까 좋은 에이전트 여덟은 여전히 반환됨. `.filter(Boolean)`이 봉쇄 장치임. 모든 팬인은 입력이 빠질 수 있다고 가정하고 설계할 것.

더 미묘한 실패는 노드끼리 밟는 것. 병렬로 파일을 쓰면 충돌함. `isolation: "worktree"`로 각 에이전트가 자기 git worktree에서 일하고 깔끔히 머지하게 함. 노드가 실제로 병렬로 쓸 때만 꺼내야 함. 모든 실행에 부과하는 기본 세금이 아니라 그 한 토폴로지를 위한 안전벨트임.

**수렴하는 순환.** 규모를 미리 모르는 일이 있음. 버그 하나 찾으면 셋이 더 드러나는 스윕 같은 것. 순환이 필요한데 수렴 안 하는 순환은 예산 마를 때까지 에이전트를 뽑는 무한 루프임.

수렴하는 패턴은 loop-until-dry임. K회 연속으로 새로운 게 안 나올 때까지 파인더를 띄움. 성패를 가르는 디테일, 그리고 거의 모두가 처음에 틀리는 지점은 **무엇에 대해 중복 제거하느냐**임. 확인된 결과가 아니라 **본 것 전부**에 대해 중복 제거해야 함. 안 그러면 기각된 발견이 매 라운드 다시 나타나고, 루프는 영영 안 마르고, 같은 막다른 길을 돈 내고 재발견하는 기계를 만들게 됨.

## 12~14. 비용, 지연시간, 자동 설계

**모델 티어링.** 모든 노드에 최고 모델이 필요하진 않음. 경계 분명하고 반복적인 노드(필드 추출, 티켓 분류)랑 진짜 판단이 실리는 노드(리포트 합성, 발견 판정)를 나눔. 워크플로에서 서브에이전트는 기본적으로 세션 모델을 상속하니까, 큰 실행이 통째로 세션 티어로 청구됨. `agent()` 호출의 `model` 옵션으로 그 노드만 다른 데로 보냄.

**토폴로지가 곧 비용이자 지연시간.** 모두가 걸려 넘어지는 선택이 `parallel()` 대 `pipeline()`임. `parallel()` 배리어는 다음 단계 시작 전에 가장 느린 노드를 전부 기다리게 함. `pipeline()`은 항목마다 독립적으로 전 단계를 흘려보내니까, 항목 A가 3단계에 있는 동안 항목 B는 1단계에 있을 수 있음. 빠른 항목이 느린 항목 뒤에서 놀지 않고 먼저 끝남.

기본은 `pipeline()`. 배리어는 한 단계가 정말로 이전 결과 전부를 동시에 필요로 할 때만. "코드가 더 깔끔하다"랑 "단계가 개념적으로 분리돼 있다"는 이유가 안 됨. 분리는 동기화랑 다름.

**Claude한테 그래프를 그리게 하기.** 미리 계획할 수 없는 일까지 손으로 그리는 걸 그만두는 단계임. 목표를 서술하면 Claude가 오케스트레이션 스크립트를 직접 씀. 진입 경로는 셋. 프롬프트에 "workflow"라는 단어를 쓰거나, 저장된 워크플로를 돌리거나(`/deep-research`가 실제 프로덕션 그래프임. scope → parallel search → fetch → adversarial verify → synthesize), ultracode를 켜서 세션의 모든 실질 작업에 워크플로를 계획하게 하거나. 좋은 실행은 `s`를 눌러 `.claude/workflows/`에 저장하면 이름으로 재실행 가능한 버전 관리 자산이 됨.

## 이번 주에 만들어볼 그래프 6개

- 전체 라우트 보안 스윕. 라우트 파일마다 서브에이전트 하나가 누락된 인증 체크를 사냥하고, 검증 패스가 리포트 전에 모든 발견을 확인
- `/deep-research`로 인용 달린 리포트. 질문을 여러 각도로 분해, 병렬 검색, 소스 중복 제거, 3표 회의론자로 모든 주장을 적대적 검증
- 모듈 파일 단위 포팅. 번역을 파일별로 팬아웃하고 각각에 테스트 스위트를 게이트로 걸고 실패를 되돌림
- diff 적대적 리뷰. diff 크기로 라우팅해서 작으면 빠른 패스, 크면 정확성·보안·성능 렌즈별 병렬 감사 후 심사 패널이 합성
- 스케줄 생태계 스캔. 한 번 저장하고 계속 재실행. 여러 소스를 병렬로 확인하고 배리어에서 영향도 순으로 랭킹한 뒤 다이제스트 작성
- 규모 미상 발견. 파인더를 병렬로 돌리고 새 발견을 본 것 전부와 대조해 중복 제거, 생존자를 검증, 두 라운드 연속 새 게 없으면 정지

## 결론

프롬프터는 질문을 하고 아키텍트는 그래프를 그림. 선형 에이전트는 천장이 아니라 첫 번째 모양이었을 뿐임. 우리가 타이핑하는 방식이랑 닮아서 모두가 먼저 집는 모양.
