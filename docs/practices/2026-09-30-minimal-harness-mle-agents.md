## 요약

자율 ML 엔지니어링 에이전트를 멀티에이전트 오케스트레이터와 검색 서브에이전트로 쌓아 올리는 흐름에 대고, **읽기·쓰기·bash만 주고 세션 하나만 돌리는 최소 하네스**를 같은 시간 예산·같은 백본으로 붙여 본 논문임. 결론은 제목 그대로 **강한 에이전트에게는 하네스가 거의 값을 못 한다**는 것이고, GLM 5.2 백본에서 최소 하네스 Malena가 MLE-bench 메달률 **62.5%**, 외부 하네스 중 최고가 **47.1%**였음.

다만 이 저장소에 더 값어치 있는 쪽은 그 숫자가 아니라 **뒤집히는 지점**임. 같은 표에서 **DeepSeek V4 Flash 백본에서는 Arbor가 50.0%로 Malena 44.4%를 앞서고, Gemma 4 31B 에서는 MLEvolve가 오라클 기준 31.1%로 최고**임. 즉 "하네스를 걷어내라"는 처방이 아니고 **백본이 약할수록 하네스가 메우던 자리가 다시 드러난다**는 결과로 읽어야 함. 그리고 멀티에이전트 개입은 깎아먹는 쪽으로 움직였음. 위임을 켜면 메달률이 **55.7% → 45.2%**, 브로드캐스트와 3중 병렬을 같이 켜면 **33.3%** 까지 내려감.

비용 쪽도 방향이 반대임. 최소 하네스가 더 쌀 것 같지만 GLM 5.2 기준 모델 비용이 **Malena $12.12 대 AiScientist $1.95**, 약 **6.2배**이고 그 대부분이 캐시 읽기 토큰임.

## 저자와 소속을 먼저 갈라야 함

Apple Machine Learning Research 사이트에 올라와 있지만 **저자 셋 모두 EPFL 소속**이고, Apple 페이지가 둘째 저자에 대해 **"work done while at Apple"** 이라고 적음. 즉 Apple 제품이나 Apple 내부 에이전트에 대한 결과가 아니고, Apple 호스팅 연구 출판물임. 이 저장소에서 Apple 태그가 붙은 다른 문서들과 같은 성격으로 읽으면 안 됨.

## 무엇을 무엇과 비교했나

| 항목 | 내용 |
|---|---|
| 최소 하네스 | **Malena.** "a single well-prompted coding agent session with a minimal set of tools". OpenCode v1.15.6 위에서 돎 |
| 추가 툴 셋 | 코딩 에이전트의 read·write·bash 위에 셋만 더함. `submission`(제출 파일 등록, 점수는 안 돌려줌), `system`(하드웨어 자원·사용률·남은 시간), `jobs`(백그라운드 실행·stdout 확인·대기·취소) |
| 비교 대상 | 오픈소스 MLE 하네스 넷. **MLEvolve, AiScientist, Arbor, ScienceFlow** |
| 백본 | GLM 5.2(기본), Kimi K3, DeepSeek V4(Flash 포함), Gemma 4 31B |
| 벤치마크 | **MLE-bench** fixed30 셋, **24시간** 예산, 1×A100 80GB·12 CPU 코어·144GB RAM. 보조로 **NatureBench** 40과제, **8시간** 예산 |

`fixed30`은 데이터나 정답 누출 문제가 있던 과제 넷을 **버리지 않고 고쳐서** 쓴 30과제 셋임. 섹션 4의 ablation은 `default29`(원본 MLE-bench에서 `bms`·`alaska2` 제외)를 씀. 유효 제출이 하나도 없는 런은 **드롭하지 않고 최악 퍼센타일로 대체**함. 이 처리 방식이 표를 읽는 전제라서 같이 봐야 함.

## 지표가 둘인 이유

이 논문이 모든 결과를 **self-select**와 **oracle** 둘로 내놓음. 둘의 차이가 이 저장소에서 반복해 온 주제와 정확히 겹침.

- **self-select**: 하네스가 **검증 점수로** 최종 제출을 고른 결과
- **oracle**: 런 안에서 만들어진 후보들의 **실제 테스트 점수 최고값**
- **selection gap**: 둘의 차. 검증 점수로 고르는 대가임

24시간·`default29`에서 Malena는 self-select **69.30**, oracle **71.18**, gap **1.876**임. 반면 Best-of-N은 gap이 **6.832pp**로 벌어짐. 후보를 많이 만드는 전략이 상한은 올리지만 **고르는 데서 다 잃는다**는 뜻임.

## 결과, 그리고 뒤집히는 지점

MLE-bench fixed30·24시간 기준 **메달률(self-select / oracle, %)** 임. 원문은 각 값에 95% 신뢰구간을 붙였는데 이 문서에는 옮기지 않았음. 효과 크기를 인용할 거면 원문 표 15를 직접 볼 것.

| 백본 | Malena | Arbor | AiScientist | MLEvolve | ScienceFlow |
|---|---|---|---|---|---|
| Kimi K3 | 60.0 / 65.6 | 60.0 / 61.1 | 52.2 / 53.3 | 50.0 / 63.3 | 표에 없음 |
| GLM 5.2 | **62.5 / 65.0** | 45.8 / 47.5 | 47.1 / 49.9 | 39.2 / 50.0 | 24.4 / 40.0 |
| DeepSeek V4 Flash | 44.4 / 48.9 | **50.0 / 51.1** | 45.6 / 45.6 | 26.7 / 40.0 | 34.4 / 40.0 |
| Gemma 4 31B | 17.8 / 22.2 | 표에 없음 | 20.0 / 23.3 | **22.2 / 31.1** | 표에 없음 |

읽는 순서는 이렇게 됨.

1. **GLM 5.2에서만 격차가 크게 벌어짐.** 요약과 초록이 드는 62.5 대 47.1이 이 행임
2. **Kimi K3에서는 Arbor가 self-select 동률**(60.0)이고 MLEvolve의 oracle이 63.3으로 Malena 65.6에 붙음
3. **DeepSeek V4 Flash에서는 Arbor가 앞섬.** 이 행만 보면 결론이 반대로 나옴
4. **Gemma 4 31B에서는 Malena가 최하위권**임. 원문이 유의하지 않다고 적은 것은 **self-select** 쪽임. 표 16의 차이가 **-4.4pp [-10.0, +1.1]** 로 0을 품음(17.8 대 22.2). **oracle 은 반대로 갈림**: 표 15가 Malena **22.2% [17.8, 26.7]**, MLEvolve **31.1% [27.8, 35.6]** 로 구간이 겹치지 않음. 두 지표를 섞어 인용하면 안 됨

논문이 주장하는 범위도 거기까지임. 저자들이 부록 G.1에서 **"Malena가 특정 베이스라인보다 못하지 않다"는 약한 주장은 잘 지지되지만, 얼마나 더 낫다는 강한 주장은 조심해서 읽어야 한다**고 스스로 적음. 24시간 런은 과제당 시드가 **3~4개**뿐이고 다른 조건들은 6~10개였음.

NatureBench(8시간, SOTA 초과율 %, 95% CI)는 백본 둘만 돌렸고 여기서도 같은 패턴이 나옴.

| 백본 | Malena | AiScientist | MLEvolve |
|---|---|---|---|
| GLM 5.2 | 21.7 [15.0, 27.5] | 17.5 [12.5, 22.5] | 10.8 [7.5, 15.0] |
| Kimi K3 | 26.7 [20.0, 32.5] | **27.1 [20.0, 35.0]** | 11.7 [7.5, 15.0] |

Kimi K3에서 점추정은 AiScientist가 높고 신뢰구간이 겹침. 원문은 NatureBench의 oracle 지표가 `/evaluate` 호출을 많이 하는 하네스에 **기계적으로 유리할 수 있다**는 단서도 달아둠.

## 멀티에이전트 개입은 전부 깎아먹었음

이 저장소의 오케스트레이터 문서들과 가장 세게 부딪히는 부분임. `fixed14` 셋·24시간 기준 **메달률(%)** 이고 `+` 는 base 위에 얹은 개입임.

| 변형 | self-select | oracle |
|---|---|---|
| base | **55.7** [48.2, 62.9] | 60.4 [53.2, 66.8] |
| +D (위임) | 45.2 [38.1, 54.8] | 47.0 [38.1, 56.0] |
| +P3 (3중 병렬) | 52.4 [42.8, 61.9] | **60.7** [53.6, 67.3] |
| +B+P3 (브로드캐스트 + 병렬) | 33.3 [23.8, 40.5] | 53.0 [45.8, 60.1] |

- **+D**는 네이티브 task 툴로 백그라운드 서브에이전트를 켜고 프롬프트로 사용을 권장한 것. 흔히 말하는 플래너·실행자 구조임
- **+P3**는 **같은 물리 머신에서** Malena 3개를 독립 실행한 것
- **+B**는 에이전트끼리 메시지를 브로드캐스트하는 툴이고 병렬과 함께만 켜짐

읽을 것은 **+P3의 두 칸 차이**임. oracle은 60.4에서 60.7로 거의 그대로인데 self-select는 55.7에서 52.4로 내려감. 병렬이 **상한을 올리는 게 아니라 고르기를 더 어렵게 만든다**는 뜻임. +B+P3에서 oracle 53.0과 self-select 33.3이 20pp 벌어진 것이 같은 현상의 극단임. 후보를 늘리는 설계를 할 거면 **고르는 쪽을 같이 설계하지 않으면 늘린 만큼 잃음.**

검색 전략 쪽(Chain, Greedy, UCB1, Best-of-N)도 **어느 것도 통계적으로 유의한 우위가 없었음**. 다만 Malena 자체는 수동 검색 방식 전부에 대해 유의한 메달률 우위가 있었고, 쌍별 신뢰구간 하한이 0.4%에서 5.6% 사이였음.

## 가장 큰 효과는 셸과 파일시스템

ablation 넷 중 **효과가 가장 컸던 것은 오케스트레이션이 아니라 실행 환경**이었음. 비교 축이 이럼.

- **Chat**: 툴 없이 chat completion 호출 하나. 모델이 전체 Python 파이프라인을 써서 내고, 하네스가 실행하고, 실패하면 에러를 붙여 다시 물어서 유효 제출이 나올 때까지 **전체 스크립트를 다시 받음**
- **Oneshot**: 툴이 있는 코딩 에이전트 세션 하나. 값싼 확인을 먼저 돌리고 프로덕션 런을 한 번 함. `main.py`·`submission.csv`·`design.md`·`score.txt` 를 내야 함. 6시간 제한

결론 문장이 **"a shell and a filesystem"** 을 채팅 인터페이스 대신 주는 것이 측정된 최대 효과라고 적음. **Chat 대 Oneshot의 구체적 수치는 이번에 확인하지 못했음.** 본문이 그림으로만 제시하고 숫자를 글로 쓰지 않았음.

저자들이 부록 G.2에서 가설로 붙인 설명이 **"post-training ate the harness"** 임. 검색·복구·멈추기 같은 행동을 예전에는 스캐폴딩이 공급했는데 지금은 코딩 에이전트 사후학습이 공급한다는 것. **가설이고 결과가 아니라고 원문이 명시함.**

## 비용은 최소 하네스 쪽이 비쌈

| 항목 | 값 |
|---|---|
| GLM 5.2 모델 비용 | Malena **$12.12**, AiScientist **$1.95** (약 6.2배) |
| 비용 구성 | Malena 쪽은 대부분 **캐시 읽기 토큰** |
| 캐시 읽기 가정 | input 비용의 **0.1배로 가정**함. 네 하네스 중 실제 캐시 적중 토큰 수를 보고하는 것이 없어서 **균일 할인을 가정한 모델값**임 |
| 단가 스냅샷 | 2026-09 OpenRouter 기준. GLM 5.2 input $0.3477/M, output $3.123/M. Kimi K3 input $0.5714/M, output $13.99/M. Gemma 4 31B input $0.1641/M, output $0.5146/M |

Kimi K3처럼 output 단가가 높은 백본에서는 **output 중심 검색을 돌리는 MLEvolve가 넷 중 가장 비싸짐**. 즉 하네스별 비용 순위가 백본 단가 구조에 따라 바뀜.

여기서 실무 결론이 하나 나옴. 세션 하나를 24시간 길게 끌면 **같은 컨텍스트를 계속 다시 읽는 비용**이 청구서의 주종목이 됨. 하네스를 걷어내면 복잡도는 줄지만 **비용이 캐시 읽기로 이동할 뿐 사라지지 않음.** [Prompt Caching In Agents](../agents/2026-07-22-prompt-caching-in-agents.md)가 다루는 지점이 그대로 비용 항목이 된 형태임.

## 짚어야 할 것

- **발행일 표기가 출처마다 다름.** arXiv v1 제출이 **2026-09-30**이고 Apple 페이지는 **"October 2026"** 으로만 적음. 이 문서는 날짜가 특정되는 arXiv 쪽을 `published`로 씀
- **학회·저널 게재 정보가 없음.** Apple 페이지가 venue를 적지 않고 arXiv 프리프린트임. 피어리뷰를 거친 결과로 인용하면 안 됨
- **코드 공개 여부를 확인할 수 없었음.** Apple 페이지에 코드 링크가 없고, 본문 서론·설정과 재현성 서술에도 프로젝트 저장소 URL이 없었음. 참조에 있는 GitHub 링크는 기반 프레임워크 OpenCode 것임. 즉 **Malena를 가져다 쓸 수는 없고 설계 설명만 있음**
- **Malena는 저자들 자신의 시스템임.** 튜닝 비대칭 가능성을 원문이 한계로 인정하고, 베이스라인에도 백본별 검증과 설정 ablation을 적용해 완화했다고 적음. 그 ablation들이 **"none of these ablations moved outcomes by more than run-to-run noise at our sample sizes"** 였다고 밝힘
- **벤치마크 오염 가능성.** MLE-bench는 사전학습 오염 노출이 그럴듯한 대상임. 저자들이 Dolos 코드 유사도와 임베딩 유사도 검사 둘을 돌려 이상 중복을 못 찾았다고 적었고, 보조로 NatureBench를 붙였음. **검사를 돌렸다는 것이 오염이 없다는 증명은 아님**
- **일반화 범위가 좁음.** 과제가 ML 엔지니어링 대회형이고, 24시간 같은 긴 단일 예산이며, 하네스 개입 검증이 거의 단일 워커 안에서 이뤄짐. 저자들이 에이전트 간 협조 프로토콜은 후속 과제로 미룬다고 적음. **앱 개발처럼 외부 제약이 많고 턴이 짧은 작업에 그대로 옮길 근거는 이 논문에 없음**
- **`## 결과` 표의 신뢰구간을 생략했음.** 이 문서는 점추정만 옮겼고, 원문 표 15에 95% CI가 붙어 있음. 백본별 역전을 "유의한 역전"으로 인용하려면 그 구간을 직접 봐야 함
- 원문 본문에 지시문·명령문 형태로 독자나 모델의 행동을 유도하는 문장은 없었음

## 유효기간

**2026-10-11 확인 기준이고 arXiv v1 기준임.** 결과 수치는 시점이 박힌 측정이라 낡지 않지만, 이 논문의 핵심 변수가 **백본 세대**라서 다음 세대 모델에서 표가 다시 그려질 수 있음. 다시 볼 때 확인할 것 둘. **v2 이상이 올라와 Chat 대 Oneshot 수치나 코드가 붙었는지**, 그리고 **학회 게재와 함께 멀티에이전트 조정 쪽 후속 연구가 나왔는지**. 후자는 저자들이 본문에서 미뤄둔 부분이고, 이 저장소의 오케스트레이터 문서들과 가장 크게 걸리는 자리임.
