## 요약

에이전트 시스템 대부분은 모델이 약해서 실패하는 게 아니라, **모델 주변이 애초에 시스템으로 설계되지 않아서** 실패함. 그런데 그 주변에는 서로 다른 세 계층이 있고, 문제를 겪을 때 어느 계층이 범인인지 가려내지 못하면 엉뚱한 걸 고침. 원문의 한 문장이 전체를 요약함.

> 모델이 결정하고, harness가 행동하게 하고, loop가 결과를 증명하게 하고, graph가 다음에 무엇이 허용되는지 통제한다.

## 30초 요약

| 계층 | 답하는 질문 | 담당 |
|---|---|---|
| **Prompt** | 이번 한 번의 호출에서 무엇이 일어나야 하나 | 지시, 스코프, 출력 형태 |
| **Harness** | 모델이 어디서 일하나 | 툴, 메모리, 파일, 권한, 샌드박스, 라우팅, 체크포인트, 트레이스, 승인 |
| **Loop** | 결과를 어떻게 증명하나 | 반복 작업과 피드백. 만들고, 증거에 대조하고, 유용한 실패 신호를 받아 다시 시도 |
| **Graph** | 다음에 무엇이 허용되나 | 노드, 분기, 조인, 병렬, 합법적 순환, 상태 전이, 종료 경로 |

Prompt는 원문에 없는 층인데, 나머지 셋과 구분해두면 진단이 쉬워짐. **프롬프트는 한 번의 호출 안에서 무엇이 일어날지 정하고, loop는 그 호출 이후에 시스템이 무엇을 할지 정함.** 그래서 loop 엔지니어링이 프롬프트 엔지니어링보다 큰 범주임.

## 왜 계속 뒤섞이나

셋 다 같은 모델 주변에 앉아 있고, 셋 다 신뢰성에 영향을 주고, 셋 다 루프처럼 보이는 무언가를 포함할 수 있음. 작은 프로토타입에서는 셋이 한 스크립트 안에 묻혀 있음. 그래서 교환 가능해 보이지만 아님.

툴을 쓰는 기본 에이전트를 보면 이렇게 갈림.

- 그 작은 순환은 **런타임**의 일부
- 툴 정의, 파일시스템, 상태 저장소는 **harness**
- 테스트하고 재시도하는 정책은 **loop** 설계 결정
- researcher, reviewer, publisher 중 무엇을 부를지는 **graph** 설계 결정

하나의 소프트웨어가 세 계층을 동시에 담을 수 있음. 깔끔한 아키텍처는 **셋을 따로 이름 붙이는 것에서** 시작함.

## Harness — 모델이 일할 자리

원문의 정의가 명확함.

> 모델은 지능이고, harness는 그 지능을 쓸모 있게 만드는 기계장치다.
> 아키텍처 다이어그램에서 모델을 지우면, 남아서 보이는 게 대개 harness다.

### 들어가는 것

| 범주 | 항목 |
|---|---|
| 컨텍스트 | 시스템 지시, 검색된 지식, 대화 상태, 작업 정책, 스킬과 운영 절차 |
| 행동 표면 | API, 브라우저 제어, 셸·코드 실행, DB, MCP 툴, 전문 에이전트 |
| 영속성 | 파일, 체크포인트, 세션 상태, 진행 로그, git 히스토리, 장기 메모리 |
| 실행 통제 | 타임아웃, 재시도 한도, 토큰·비용 예산, 모델 라우팅, 핸드오프, 승인 게이트 |
| 안전 | 격리 환경, 최소권한, allow list, 시크릿 처리, 사람 인증 |
| 관측성 | 트레이스, 툴 입출력, 상태 전이, 비용과 지연시간, 평가 결과 |

### 여기서 시작해야 하는 신호

작업이 컨텍스트 윈도우 하나보다 길어지면 harness가 결정적이 됨. 몇 시간 일하는 코딩 에이전트는 채팅 히스토리에 의존할 수 없고, **다른 세션이 이해할 수 있는 지속적 산출물**이 필요함.

- 워크스페이스를 점검하는 initializer
- 무엇이 끝났고 무엇이 남았는지 설명하는 progress 파일
- 동작하는 상태를 보존하는 git 커밋
- 위험한 작업 전 체크포인트
- 명확한 증거를 만들어내는 검증 툴

에이전트가 이런 상태면 harness부터 손봐야 함. 필요한 능력에 접근 못 함, 세션 간 진행을 잃음, 권한이 너무 넓음, 환경마다 다르게 행동함, 멈추고 검사하고 재개할 수 없음, 아무도 실패를 재구성할 수 없음.

## Loop — 결과를 증명하는 순환

목표는 에이전트를 영원히 반복시키는 게 아니라, **한 번의 시도를 관리되는 프로세스로 바꾸는 것**임.

### 가장 중요한 규칙

> 확신을 근거로 루프를 돌리지 말고 **증거를 근거로** 돌려라.
> "에이전트가 끝났다고 말했다"는 증명이 아니다. "테스트가 통과했고 출처가 해소되고 리뷰어가 diff를 승인했다"가 증명이다.

체크는 결정론적일 수도 있음. 테스트 통과, 스키마 검증, 링크 해소, 숫자 대조, 컴파일. 아니면 리뷰어가 필요할 수도 있음. 논증이 완결적인지, 톤이 청중에 맞는지, 증거가 결론을 지지하는지, 변경 범위가 맞는지.

### 쓸모 있는 loop의 7요소

1. **트리거** — 다음 사이클을 시작하는 것. 요청, 스케줄, 웹훅, 실패한 테스트, 새 문서, 평가자 결과
2. **목표** — "계속 개선"이 아니라 도달할 측정 가능한 상태
3. **상태** — 전체 히스토리를 재생하지 않고도 다음 시도가 알아야 할 것
4. **행동 정책** — 에이전트가 바꾸고 호출하고 위임하고 지출할 수 있는 범위
5. **증거** — 테스트, 인용, diff, 지표, 스키마, 사람 리뷰
6. **피드백** — 무엇이 실패했고 무엇을 바꿔야 하는지에 대한 압축된 설명
7. **정지 규칙** — 성공, 최대 시도 횟수, 예산 소진, 타임아웃, 하드 에러, 사람 에스컬레이션

### loop는 쌓임

- **agent loop** — 작업을 수행
- **verification loop** — 작업을 검사
- **event loop** — 새 작업이 도착하면 시스템을 깨움
- **improvement loop** — 프로덕션 트레이스를 연구해 **harness 자체를 바꿈**

비용은 명백함. 재시도, 채점자, 리뷰어마다 지연시간과 지출이 붙음. **실패의 기대비용이 검증비용보다 클 때** loop를 추가함.

## Graph — 다음에 무엇이 허용되나

graph는 "에이전트가 어떻게 일해야 하나"가 아니라 **"다음에 무엇이 실행될 수 있나"**를 물음. 작업이 노드, 허용된 전이가 엣지, 상태가 그래프를 통과함.

### graph 엔지니어가 실제로 결정하는 것

- **노드 경계** — 어떤 작업이 일반 코드에, LLM 호출에, 전문 에이전트에, 사람 리뷰 단계에 속하는지
- **상태 스키마** — 각 노드가 읽고 갱신할 수 있는 것, 병렬 결과를 어떻게 병합하는지
- **라우팅 조건** — 어떤 증거가 작업을 전진·후진·측면·에스컬레이션으로 보내는지
- **동시성** — 무엇이 병렬로 돌고 무엇이 조인을 기다려야 하는지
- **순환과 종료** — 재시도가 합법인 곳, 허용 횟수, 순환을 안전하게 만드는 조건
- **지속성** — 실행이 체크포인트되는 곳, 중단 후 재개 방식

### 언제 격식을 갖출 값어치가 있나

의미 있는 분기, 병렬 전문가, 승인, 복구 경로, 상태를 가진 핸드오프가 있을 때 씀. **단계가 여러 개라는 이유만으로 graph에서 시작하지 말 것.** 유능한 에이전트 하나가 툴 셋으로 풀 수 있으면 graph는 값어치 없이 구조만 더함.

또 다른 실패 모드가 있음. 작업을 이해하기 전에 워크플로를 형식화하면, **틀린 가정을 인코딩한 아름다운 다이어그램**이 나옴. 단순한 harness로 시작해서, 실제 트레이스를 연구하고, 안정적으로 남는 경로만 형식화할 것.

## 셋이 한 시스템에서 어떻게 겹치나

사실을 다루는 업계 브리핑을 만드는 리서치·발행 에이전트를 예로 들면 이렇게 배치됨.

- **harness**가 제공: 브라우저와 검색 툴, 소스 저장소, 작업 공간, 인용 검사, 권한과 승인 규칙, 체크포인트와 트레이스
- **graph**가 경로를 통제. 원문은 이 경로를 다이어그램으로만 보여줘서 노드 구성은 옮기지 못했음. 아래 loop 설명에 등장하는 리서치 → 초안 → 팩트체크가 그 경로의 노드로 보임
- **loop**는 그 경로 안에 산다. 리서치 노드는 소스 커버리지가 충분해질 때까지 검색하고, 초안 노드는 스타일 채점자가 통과할 때까지 고치고, 팩트체크 노드는 막연한 거부 대신 **정확히 어떤 주장이 근거 없는지** 되돌려줌

중첩이 핵심임.

```
harness
 └─ graph
     └─ loop
```

**graph는 harness 안에서 돌고, loop는 graph의 일부 안에서 돌고, harness가 그 loop들이 필요한 툴과 상태와 증거를 공급함.**

## 증상으로 계층 찾기

용어를 두고 다투는 것보다 이 표가 유용함. **먼저 실패를 소유한 계층을 찾고, 그 계층을 먼저 고칠 것.**

| 증상 | 범인 계층 | 손댈 곳 |
|---|---|---|
| 필요한 툴이 없거나 툴이 불안정함 | Harness | 행동 표면, 툴 스키마 |
| 세션 사이에 진행이 사라짐 | Harness | 영속성, 체크포인트 |
| 왜 실패했는지 재구성 못 함 | Harness | 관측성, 트레이스 |
| 권한이 너무 넓음 | Harness | 안전, 최소권한 |
| 같은 실수를 배우지 않고 반복함 | Loop | 피드백 신호, 증거 정의 |
| 영원히 재시도하며 예산을 태움 | Loop | 정지 규칙 |
| "다 했다"는데 실제로는 안 됨 | Loop | 증거를 결정론적 체크로 |
| 자기 작업을 자기가 채점함 | Loop | 격리된 리뷰어 컨텍스트 |
| 분기가 코드 안에 숨어 아무도 검사 못 함 | Graph | 노드와 엣지를 명시화 |
| 병렬 결과 병합이 뒤엉킴 | Graph | 상태 스키마, 조인 |
| 승인 지점이 임의적임 | Graph | 라우팅 조건 |
| 출력 형태가 매번 다름 | Prompt | 스키마, 출력 계약 |
| 스코프를 넘어 일함 | Prompt | 스코프 제약 지시 |

## 값비싼 실수 5가지

**graph를 너무 일찍 만든다.** 유능한 에이전트가 그 일을 하는 걸 보기 전에 상상한 업무 프로세스를 40개 노드로 옮기지 말 것. 트레이스가 먼저, 형식화가 나중.

**만든 쪽이 자기를 채점한다.** 자기 검토는 원래 시도와 같은 사각지대를 공유함. 가능하면 결정론적 체크, 주관적 체크에는 **격리된 리뷰어 컨텍스트**, 영향 큰 행동에는 사람 승인.

**loop를 "계속 시도"로 정의한다.** 무한 재시도는 신뢰성이 아니라 비용 유출임. 모든 사이클에 새 증거, 최대 시도 횟수, 이름 붙은 에스컬레이션 경로가 필요함.

**harness를 창고로 만든다.** 툴이 많아지면 자동으로 나아지지 않음. 붐비는 툴셋은 선택 오류를 늘리고, 시끄러운 컨텍스트는 혼란을 늘리고, 넓은 권한은 위험을 늘림. **작업을 완수할 수 있는 가장 작은 환경**을 줄 것.

**오케스트레이션 실패를 모델 탓으로 돌린다.** 더 강한 모델이 낡은 상태, 깨진 API, 모호한 툴 스키마, 없는 종료 조건을 고쳐주지 않음. **모델이 문제라는 걸 증명하기 전에 모델을 올리지 말 것.**

## 조합 순서 — 어디서 시작할까

원문은 순서를 명시하지 않는데, 이 저장소의 다른 문서들과 합치면 이렇게 정리됨.

**1단계. Prompt로 시작.** 한 번의 호출로 되는 일이면 여기서 끝. [Prompting Claude Opus 5](../prompting/2026-08-10-prompting-claude-opus-5.md)가 말하듯 Opus 5에서는 오히려 **검증 지시를 빼는 것**이 이득임. 모델이 이미 하는 일을 지시로 중복시키면 비용만 늘어남.

**2단계. Harness.** 작업이 컨텍스트 윈도우를 넘거나 세션을 넘어가면 여기로. 이 단계에서 [Prompt Caching](../agents/2026-07-22-prompt-caching-in-agents.md)이 걸림. 툴 로드아웃과 스킬 로스터를 세션 시작 시 고정해야 하고, 중간에 바꾸면 그 뒤가 통째로 재과금됨.

**3단계. Loop.** 실패의 기대비용이 검증비용보다 클 때. [Eval Engineering](./2026-08-01-eval-engineering-merge-gate.md)이 이 단계의 실무 매뉴얼임. 판정자 편향, 경로 채점, 폭발 반경 기준 게이팅이 전부 loop 설계에 속함.

**4단계. Graph.** 의미 있는 분기와 병렬 전문가와 승인이 생겼을 때. [Graph Engineering with Claude](./2026-07-20-graph-engineering-with-claude.md)가 구현이고 [Graph Engineering 해설](./2026-07-24-graph-engineering-explained.md)이 비용과 한계임. 후자의 Bun 재작성 $165,000 사례가 이 단계의 청구서를 보여줌.

**교차 관심사.** [Memory Engineer](./2026-08-02-memory-engineer.md)는 harness의 영속성에 속하지만 loop의 상태 설계와도 맞물림. [비용 관리](./2026-08-07-managing-ai-coding-costs.md)는 네 단계 전부에 걸림.

건너뛰지 말아야 할 순서가 하나 있음. **loop 없이 graph를 만들면** 노드끼리 서로를 감시하는데 아무것도 검증되지 않는 상태가 됨. Graph Engineering 해설이 말하는 **앵커** 문제임.

## 프로덕션 체크리스트

원문이 계층별로 정리한 것.

**Harness** — 툴이 좁고 문서화되고 관측 가능한가 · 상태가 세션을 넘어 지속되는가 · 권한이 최소인가 · 운영자가 멈추고 검사하고 재개할 수 있는가 · 중요한 행동을 트레이스로 재구성할 수 있는가

**Loop** — 무엇이 성공을 증명하는가 · 실패 후 어떤 피드백이 돌아오는가 · 재시도는 몇 번인가 · 예산이 소진되면 어떻게 되는가 · 사람 판단이 필요한 곳은 어디인가

**Graph** — 어떤 경로가 결정론적이어야 하는가 · 어디서 병렬이 가능한가 · 어떤 상태가 공유되는가 · 조인과 승인과 복구 경로는 어디인가 · 어떤 순환이 합법이고 어떻게 종료되는가

**평가** — 팀이 실제 트레이스를 재생할 수 있는가 · 같은 과제로 버전을 비교할 수 있는가 · 개선을 특정 변경에 귀속시킬 수 있는가

**운영** — 비용과 지연시간이 모니터링되는가 · 실패율이 노드와 툴별로 보이는가 · 사람 개입이 측정되는가 · 과제 단위 성공률이 프로덕션에서 측정되는가

## 한 줄로 기억하기

> harness 엔지니어링은 모델을 **운영 가능**하게 만들고, loop 엔지니어링은 작업을 **반복 가능하고 검증 가능**하게 만들고, graph 엔지니어링은 복잡한 실행을 **명시적이고 통제 가능**하게 만든다.

어느 것도 다른 것을 대체하지 않음. 완벽한 graph도 상태를 잃는 에이전트를 구하지 못하고, 완벽한 harness도 loop에 증거와 정지 규칙이 없으면 돈을 낭비하고, 강한 loop도 분기와 병렬과 승인이 임시 코드에 숨어 있으면 운영이 어려워짐.
