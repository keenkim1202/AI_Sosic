## 요약

**2026-10-28**에 Messages API 와 토큰 카운팅의 요청 크기 상한이 **32MB 에서 128MB** 로 올라갔음. 1차 Claude API 한정임. 그런데 사진이나 스캔을 올리는 앱에서 **이 숫자가 먼저 걸릴 일은 거의 없음.** 먼저 걸리는 것은 **이미지 한 장당 10MB(base64 기준)** 와, 한 요청의 이미지가 **20장을 넘는 순간 그 요청의 모든 이미지에 더 좁은 치수 제한이 걸리는** 규칙임. 그리고 치수를 넘긴 이미지는 거절되지 않고 **조용히 축소**되는데, 축소를 결정하는 것은 변 길이가 아니라 **비주얼 토큰 예산**이라 1,568px 아래 이미지도 축소됨. 올라간 상한이 안 닿는 곳도 있음. **Sessions·Agents·Environments 는 그대로 32MB** 이고, Bedrock 은 **20MB**, Google 운영 Google Cloud 는 **30MB** 임.

## 엔드포인트마다 상한이 다름

1차 Claude API 기준 표임. 원문 표를 그대로 옮긴 것이고 초과하면 **413 `request_too_large`** 임.

| 엔드포인트 | 최대 요청 크기 |
|---|---|
| Messages, 토큰 카운팅 | **128MB** (2026-10-28 에 32MB 에서 올라감) |
| Message Batches | 256MB |
| Files API | 500MB |
| Sessions, Agents, Environments | **32MB** |

마지막 줄이 이 변경의 범위를 가름. 이번 인상은 Messages 와 토큰 카운팅만이고, **Managed Agents 쪽 세 엔드포인트는 32MB 에 남아 있음.** 세션에 큰 입력을 밀어넣는 구성([Managed Agents 다이내믹 워크플로](../agents/2026-10-09-managed-agents-dynamic-workflows.md))이면 이번 인상의 수혜가 없음.

플랫폼을 가로지르면 더 좁아짐. 파트너 운영 쪽이 특히 낮음.

| 플랫폼 | Messages·토큰 카운팅 상한 |
|---|---|
| Claude API (1차) | 128MB |
| Claude Platform on AWS | 32MB |
| Claude Models on Google Cloud (Anthropic 운영) | 32MB |
| Microsoft Foundry | 32MB |
| Claude Models on Google Cloud (Google 운영) | 30MB |
| Amazon Bedrock | **20MB** |

즉 **같은 요청이 1차 API 에서 통과하고 Bedrock 에서 413 이 됨.** 플랫폼을 섞어 쓰거나 폴백 경로를 다른 플랫폼으로 잡아둔 구성이면 가장 낮은 상한을 기준으로 설계해야 함. 문서 자신이 "Consult your platform's documentation for current values"로 값이 움직일 수 있다고 적어 뒀음.

## 이미지 쪽 제한이 실제 천장임

Vision 문서의 `Request limits` 절이 앱 설계에 직접 들어오는 숫자를 들고 있음.

- 한 요청의 이미지 개수: **200K 컨텍스트 모델은 100장**, 그 밖의 모델은 **600장**
- 이미지 한 장의 최대 치수: **8000x8000px**
- 이미지 한 장의 최대 크기: 1차 Claude API 와 Google 운영 Google Cloud 는 **10MB(base64 인코딩 기준)**, Bedrock 은 **5MB**

세 번째 항목에 함정이 있음. 상한이 **인코딩된 크기**에 걸림. base64 는 3바이트를 4문자로 바꾸므로 약 4/3배가 되고, 그래서 10MB 상한은 **원본 바이트로 치면 7.5MB 쯤**임. 이 환산은 원문에 없는 산술이니 경계에서는 실제로 인코딩해 재 보는 편이 맞음.

그리고 iOS 쪽에서 먼저 밟는 것이 **포맷**임. 지원 목록은 **JPEG, PNG, GIF, WebP** 네 개이고 애니메이션은 지원하지 않아 **첫 프레임만** 쓰임. 목록에 **HEIC·HEIF 가 없음.** iPhone 카메라 기본 포맷이 HEIC 이므로 사진 라이브러리에서 꺼낸 데이터를 그대로 보낼 수 없고, 앱에서 JPEG 나 PNG 로 변환하는 단계가 반드시 들어감. 이것은 포맷 목록에서 읽은 판단이고 원문이 HEIC 를 이름으로 언급한 것은 아님.

## 스무 장째에서 규칙이 바뀜

이 절이 이 문서에서 제일 값어치 있는 부분임. 한 요청에 이미지가 **20장을 넘으면 그 요청의 모든 이미지에 더 좁은 치수 제한**이 걸림. 20장까지는 안 걸리던 이미지가 21장째를 붙이는 순간 전부 거절 대상이 됨.

무엇이 그 20장 계산에 들어가는지가 중요함. 원문이 넷을 명시함.

- 그 요청의 모든 `image` 블록
- **앞선 턴에서 보낸 이미지를 다시 보내는 것**도 포함됨
- `tool_result` 안에 중첩된 이미지도 포함됨. computer use 툴에 돌려주는 스크린샷이 예로 적혀 있음
- Bedrock 과 Google 운영 Google Cloud 에서는 **PDF 같은 document 블록도** 이 임계값에 같이 셈

둘째 항목이 멀티턴 대화에서 조용히 터지는 자리임. 사용자가 한 턴에 사진 두 장씩 올리는 UI 라면 **11번째 턴부터** 히스토리 누적만으로 임계값을 넘김. 거절은 `invalid_request_error` 이고 메시지에 "many-image requests"와 현재 픽셀 상한이 들어감. 즉 상한값 자체는 에러 메시지로만 알 수 있고 문서에 숫자로 박혀 있지 않음.

문서가 준 처방은 둘이고 **모든 플랫폼에서 안전한 쪽**으로 적혀 있음.

- 이미지마다 두 변이 **3,000px 를 넘지 않게** 리사이즈하거나
- 요청의 이미지·문서 블록을 **20개 이하로** 유지하기

앱 쪽 결론은 후자임. 히스토리에 이미지를 무한히 쌓지 않고 창을 두는 설계가 필요하고, 이것은 [서버측 compaction](./2026-09-20-claude-api-compaction.md)이 텍스트에 대해 하던 일을 이미지에 대해서도 해야 한다는 뜻임.

## 축소는 에러가 아니라 조용히 일어남

치수를 넘긴 이미지는 거절되지 않고 **축소된 뒤 처리**됨. 축소 규칙은 두 한도를 동시에 만족하는 가장 큰 비율 유지 크기임.

| 티어 | 대상 모델 | 최대 변 길이 | 최대 비주얼 토큰 |
|---|---|---|---|
| High-resolution | Claude 4.7 이상 모델 | 2,576px | 4,784 |
| Standard | 그 밖의 모델 | 1,568px | 1,568 |

비주얼 토큰은 **28x28 픽셀 패치 하나**가 1토큰이고 비용은 `⌈너비/28⌉ × ⌈높이/28⌉` 임. 여기서 자주 틀리는 것이 **변 길이가 아니라 토큰 예산이 축소를 결정한다**는 점임. 원문이 든 예가 정확함. **130DPI 로 스캔한 A4 는 1075x1520px** 인데 두 변 모두 1,568px 아래임. 그런데 토큰이 `39 × 55 = 2145` 라 standard 티어에서는 **924x1307 로 축소**됨. 1920x1080 스크린샷도 1568x882 가 아니라 **1456x819** 가 됨. 축소 뒤에는 아래·오른쪽 변을 28의 배수로 **패딩**함(924x1307 은 924x1316).

좌표를 다루는 작업이면 이게 바로 버그가 됨. 영수증이나 서식에서 바운딩 박스를 받아 화면에 그리는 앱은 Claude 가 돌려준 좌표가 **축소된 이미지의 픽셀**이라, 원본에 그대로 찍으면 어긋남.

막는 수단이 있음. 이미지 블록에 `transformations: {"oversized_image": "error"}` 를 달면 축소될 이미지가 **400 `invalid_request_error`** 로 떨어지고, 에러 메시지가 현재 치수와 들어갈 수 있는 최대 치수를 같이 알려 줌. 기본값은 `"downsize"` 라 아무것도 안 하면 조용히 축소됨. 다만 이것으로 안 되는 것도 명시돼 있음.

- **하드 상한은 별개의 거절**임. 8,000px 과 위의 many-image 제한은 이 설정으로 통과되지 않음
- URL 이나 `file_id` 로 보낸 이미지는 바이트를 받은 뒤 검사되고, **에러 메시지에 위치가 없어서 어느 이미지가 걸렸는지 안 나옴.** 인라인 base64 만 위치로 지목됨
- `document` 블록은 이 필드를 받지 않음. **PDF 페이지는 서버에서 치수를 모르는 상태로 래스터화**되므로 PDF 좌표는 애초에 원본에 되매핑할 수 없음. 좌표가 필요하면 앱에서 페이지를 직접 이미지로 만들어 보내야 함
- computer use·browser use 의 `tool_result` 이미지는 예외적으로 **축소 대신 거절**됨. 앱에서 미리 줄여야 함

## 토큰 카운팅이 통과를 보장하지 않음

이 저장소는 [Claude for Foundation Models](../agents/2026-10-25-claude-for-foundation-models.md)에서 그 경로에 토큰 카운팅이 없다는 것을 문제로 적어뒀음. 직접 API 를 때리는 쪽은 토큰 카운팅을 쓸 수 있는데, 이미지에 대해서는 보장 범위가 좁음.

토큰 카운팅 엔드포인트는 이미지를 **완전히 처리하지 않고 치수만으로 토큰 비용을 추정**함. 그래서 **카운팅이 성공해도 Messages 에서 거절될 수 있음.** 원문 문장이 "a successful count doesn't mean the image is within the Messages API's request limits"임. `transformations` 는 인라인 base64 이미지에 대해서만 카운팅에서도 집행되고, URL·`file_id` 이미지는 **가져오지 않고 거절**하므로 그쪽 검사는 Messages 시점으로 밀림.

즉 전송 전 검사를 토큰 카운팅 하나로 세우면 안 됨. 치수·바이트 크기·블록 개수는 앱에서 직접 세야 하는 값임.

## PDF 는 페이지 수로 한 번 더 걸림

| 요건 | 한도 |
|---|---|
| 최대 요청 크기 | 128MB (1차 Claude API, 플랫폼마다 다름) |
| 요청당 최대 페이지 | **600. 요청의 컨텍스트 창이 1M 미만이면 100** |
| 포맷 | 표준 PDF. 암호·암호화 없음 |

두 한도 모두 **PDF 와 같이 보낸 다른 콘텐츠까지 포함한 전체 페이로드**에 걸림. 그리고 페이지마다 **이미지로 처리**되므로 글씨가 작고 표가 많은 문서는 페이지 상한에 닿기 전에 **컨텍스트 창이 먼저 참다**고 문서가 경고함. 큰 PDF 는 Files API 를 써도 페이지 상한 전에 실패할 수 있다고 같이 적어 뒀음.

컨텍스트 창 기준으로 100과 600이 갈리는 것이 설계에 들어옴. 1M 창 모델에서는 600페이지까지 되는데, 그 지점이 비용과 충돌함. 아래가 그 자리임.

## 비용은 장수가 아니라 티어로 갈림

같은 이미지의 토큰 비용이 티어로 최대 **3배 가까이** 갈림. 원문 표에서 두 줄만 가져오면 이렇음.

| 이미지 크기 | Standard 축소 결과 / 토큰 | High-resolution 축소 결과 / 토큰 |
|---|---|---|
| 1920x1080 (2.07MP) | 1456x819 / **1,560** | 축소 없음 / **2,691** |
| 3840x2160 (8.29MP) | 1456x819 / **1,560** | 2576x1449 / **4,784** |

원문이 단가까지 곱해 둔 예가 있음. 1000x1000 이미지가 Haiku 4.5 의 입력 $1/MTok(standard)에서 **1,000장당 약 $1.30**, Opus 5.5 의 $4/MTok(high-resolution)에서 **약 $5.18**, 4K 이미지는 **약 $19.14** 임.

여기가 이 저장소의 [Claude Haiku 5.5](../models/2026-10-07-claude-haiku-5-5.md)와 정면으로 만남. 그 모델은 **프롬프트가 100,000 토큰을 넘으면 입력·출력·캐시 단가가 전부 5배**가 됨. high-resolution 티어 한 장이 최대 4,784 토큰이므로, 산술로는 **그런 이미지 21장이면 10만 토큰 경계**임. 사진 스무 장을 한 요청에 넣는 UI 가 위의 many-image 임계값과 **거의 같은 자리에서 가격 구간도 넘기게 됨.** 다만 이 계산에는 유보가 있음. Vision 문서는 티어를 "Claude 4.7 이상"으로만 적고 **모델 ID 를 나열하지 않아서** Haiku 5.5 가 어느 티어인지 문서로 확인할 수 없었음. 버전 번호로 보면 high-resolution 쪽이지만 확인된 사실로 쓰면 안 됨.

문서가 직접 적은 처방은 하나임. **computer use, 스크린샷 이해, 밀도 높은 문서처럼 고해상도가 실제로 필요한 경우가 아니면 보내기 전에 다운샘플링할 것.** 지연시간도 같이 줄어듦.

## Files API 로 넘기는 경로와 그 대가

원문이 이미지가 많거나 PDF 가 클 때 권하는 경로가 Files API 임. 한 번 올리고 `file_id` 로 참조하면 요청 페이로드가 작아짐. 숫자는 이렇음.

- 파일 하나 **500MB**, 조직 전체 **1TB**
- 업로드·다운로드·목록·메타데이터·삭제는 **전부 무료.** 메시지에서 쓴 파일 내용만 입력 토큰으로 과금됨
- 파일 관련 호출은 **분당 약 500회**
- 베타가 끝났고 **베타 헤더가 필요 없음**
- 만료는 업로드할 때 `expires_in_seconds` 로만 설정하고 **3,600초(1시간)에서 7,776,000초(90일)** 사이임. **올린 뒤에는 바꿀 수 없음**

대가가 둘 있고 둘 다 앱 설계에 직접 걸림.

첫째, **격리 경계가 워크스페이스임.** 파일은 사용자·대화·세션에 묶이지 않고, 그 워크스페이스에 접근 가능한 **아무 API 키나 아무 파일을 읽을 수 있음.** 문서가 "Never accept `file_id` values from end users or other untrusted sources"로 못을 박았고, 멀티테넌트 앱이면 **테넌트마다 워크스페이스를 따로 만들라**고 적음(조직당 최대 100개). 이것은 [User Profiles](./2026-10-20-user-profiles-end-customer-attribution.md)가 푼 문제와 다른 축임. 그쪽은 **집행의 폭발 반경**을 사용자 단위로 좁히는 것이고, 이쪽은 **데이터 접근 경계**이며 여전히 워크스페이스 단위임. 사용자 100만 명짜리 앱에 워크스페이스 100개는 답이 아니므로, 결론은 `file_id` 를 서버측 참조로만 두고 사용자와의 매핑을 앱이 들고 있는 것임.

둘째, **올린 파일은 다시 내려받을 수 없음.** 업로드한 파일은 `downloadable: false` 이고 다운로드를 시도하면 400 임. 내려받을 수 있는 것은 스킬이나 코드 실행 툴이 **만든** 파일뿐임. 앱이 원본을 자기 저장소에 따로 두지 않고 Files API 를 캐시처럼 쓰면 되돌릴 방법이 없음. 그리고 Files API 는 **zero data retention 대상이 아님**(명시적으로 삭제하거나 만료될 때까지 보관).

만료된 파일의 동작도 미리 알아야 함. 만료되면 내용 다운로드는 404, **그 파일을 참조하는 Messages 요청은 추론 전에 실패**, 메타데이터는 최대 30일 더 읽힘. 즉 만료는 "지워진다"가 아니라 "참조가 깨진다"에 가깝고, 문서 자신도 **보장된 삭제 수단이 아니라 수명주기 기능**이라고 구분해 적어 뒀음.

## 앱에 붙일 때의 순서

위 내용을 앱 쪽 작업 순서로만 추리면 이렇음.

1. HEIC 를 JPEG 나 PNG 로 변환하는 단계를 둠. 지원 포맷 넷 밖은 애초에 못 보냄
2. 보내기 전에 **티어에 맞는 크기로 직접 리사이즈**함. 좌표를 쓰는 기능이면 `transformations: {"oversized_image": "error"}` 를 같이 달아 축소를 에러로 바꿈
3. 한 요청의 **이미지·문서 블록 수를 20개 이하로** 유지함. 히스토리에 쌓인 이미지가 같이 센다는 것을 기억할 것
4. 이미지가 많거나 PDF 가 크면 Files API 로 올리고 `file_id` 로 참조함. 단 `file_id` 는 **서버측 참조로만** 두고 클라이언트에서 받지 않음
5. 전송 전 검사를 토큰 카운팅에만 맡기지 않음. 바이트 크기·치수·블록 개수는 앱이 직접 셈
6. 폴백 경로가 다른 플랫폼이면 **가장 낮은 상한(Bedrock 20MB)** 을 기준으로 잡음

## 짚어야 할 것

- **인상 자체는 한 줄짜리 릴리스 노트임.** 왜 128MB 인지, 왜 Messages 와 토큰 카운팅만인지는 적혀 있지 않음. Sessions 쪽이 32MB 에 남은 이유도 확인할 수 없었음
- **many-image 임계값의 실제 픽셀 상한이 문서에 없음.** 에러 메시지가 알려준다고만 적혀 있고, 문서가 주는 숫자는 "모든 플랫폼에서 안전한" 3,000px 권고뿐임. 실제 상한은 확인할 수 없었음
- **모델별 해상도 티어가 ID 로 나열돼 있지 않음.** "Claude 4.7 이상"이라는 서술만 있어서 특정 모델이 어느 티어인지 문서로 못 가름. 위의 10만 토큰 산술은 그래서 확정이 아님
- **base64 10MB 를 원본 7.5MB 로 환산한 것은 원문에 없는 산술임.** 인코딩 비율에서 나온 값이고 경계에서는 직접 재야 함
- **HEIC 를 변환해야 한다는 것은 지원 포맷 목록에서 읽은 판단임.** 원문이 HEIC 를 이름으로 언급하지는 않음
- **직접 호출해 본 것이 아니라 문서만 읽었음.** 413 과 400 의 실제 응답 본문, many-image 에러 문구는 원문 표기를 옮긴 것임
- 같은 릴리스 노트의 **2026-10-29 Usage and Cost Analytics API** 는 조직 단위 분석이라 이 문서 범위 밖임

## 유효기간

**2026-10-30 확인 기준이고 인상 자체는 2026-10-28 항목임.** 날짜가 박힌 사실(32MB 에서 128MB 로 올라갔다는 것)은 낡지 않지만 **표에 적힌 값들은 전부 움직이는 종류**이고 문서 자신이 플랫폼별 값은 각 플랫폼 문서에서 확인하라고 적어 뒀음. 다시 볼 때 확인할 것 셋. **Sessions·Agents·Environments 의 32MB 가 같이 올라갔는지**, **해상도 티어 표에 모델 ID 가 나열되기 시작했는지**(나열되면 위의 10만 토큰 유보가 풀림), 그리고 **many-image 임계값의 픽셀 상한이 문서에 숫자로 적혔는지**. 지원 포맷 목록에 HEIC 가 들어오는지도 같이 볼 값어치가 있음. 시작점은 [API 릴리스 노트](https://platform.claude.com/docs/en/release-notes/api)에서 request size 와 vision 항목이 더 붙었는지임.
