## 요약

2023년에 Python 으로 만든 Messages API 를 Rust 로 통째로 다시 쓴 기록임. **2024년 초부터 2026년 가을까지 API 트래픽이 약 1,800배**로 늘어난 것이 동기고, 결과는 **요청당 CPU 약 70% 감소, 요청당 메모리 80% 이상 감소, 중간값 TTFT 약 20% 감소**임. 하지만 이 저장소에서 읽을 값어치는 그 수치가 아니라 **검증을 어떻게 세웠는가** 쪽임.

출발점이 이 글의 전부임. **약 700개 통합 테스트가 있었는데 그게 검증기 역할을 못 했음.** 포팅한 테스트를 감사하니 **약화된 단정이 100개 이상** 나왔고, 애초에 조합이 덮이지 않았음(**이진 옵션 20개만으로 100만 조합 이상, 하나당 1초면 모델 하나에 약 12일**). 그래서 **프로덕션 트래픽을 검증기로 승격**시켰음. 모델을 한 번만 돌리고 그 출력을 Rust 쪽에 재생해서 두 버전이 같은 모델 출력에서 출발하게 만들고, 프롬프트가 갈리는 지점을 지문으로 기록함. **4월에 테스트는 약 98% 통과했는데 프로덕션 입력 일치율은 약 24%** 였다는 대조가 이 글의 핵심 수치임.

그 위에 **inner / outer / memory 세 루프**를 얹었고, 사람의 노동은 개별 수정 지시에서 **규칙과 검사를 쓰는 쪽**으로 옮겼음. 일치율은 **5월 초 6.5%** 까지 내려갔다가 **8월 99.6%** 로 끝남.

## 부분 재작성이 먼저 실패한 이유

전체 재작성 전에 응답 파싱만 Rust 로 옮겨 본 적이 있음. **CPU 사용량이 약 8~10% 줄었지만** 거기서 멈췄음. 이유가 명확함.

> "Each token now crossed between Python and Rust three times."

토큰 하나가 경계를 세 번 넘으니 추가 복잡도가 이득을 못 넘었다는 것임. 하이브리드 구간이 비용을 먹는다는 흔한 결론인데, **그래서 전체 재작성으로 갔고 그 결정이 검증 문제를 통째로 불러왔음.** 부분 이식은 검증 범위가 작고, 전체 이식은 "두 시스템이 같은가"를 증명해야 함.

## 테스트가 검증기가 되지 못한 이유

이 절이 `## 요약`보다 중요함. 테스트 스위트가 있는데도 못 쓴 사유가 셋으로 갈림.

| 사유 | 내용 |
|---|---|
| 구현에 묶여 있었음 | 테스트가 Python 구현에 결합돼 있었고, 포팅하면서 **약화된 단정이 100개 이상** 나옴. 통과가 "코드가 맞다"가 아니라 "테스트가 바뀌었다"를 뜻할 수 있음 |
| 불완전했음 | **이진 옵션 20개만으로 100만 조합이 넘고**, 하나당 1초로 쳐도 모델 하나에 **약 12일**. 조합을 테스트로 덮는 경로가 애초에 없음 |
| 목표가 움직였음 | 이식하는 동안 Python API 도 계속 바뀜. 패리티가 고정된 과녁이 아니었음 |

첫째 항목이 에이전트를 쓰는 쪽에서 특히 위험함. **에이전트가 포팅한 테스트의 단정을 느슨하게 만들면 녹색 CI 가 거짓 신호가 됨.** [Eval Engineering](./2026-08-01-eval-engineering-merge-gate.md)이 "지금 보는 점수는 판정자에 대한 점수이기도 함"으로 시작하는 것과 같은 자리이고, [자기개선 에이전트 루프의 7가지 규칙](./2026-08-10-self-improving-agent-loops.md)이 말하는 "점수는 잘 나오고 동작은 나빠진" 최적화의 실물 사례임.

## 프로덕션 트래픽을 검증기로 올리기

핵심 설계가 둘임.

**첫째, 모델을 한 번만 돌림.** Claude 의 응답은 같은 입력에도 갈리므로 두 버전에 각각 돌리면 차이가 어디서 왔는지 알 수 없음. 그래서 모델 출력을 **한 번 받아 Rust 쪽에 재생**해서, 두 구현이 동일한 모델 출력에서 출발하도록 만들었음. 즉 비교 대상을 모델이 아니라 **프롬프트 조립과 응답 처리**로 좁힌 것임.

**둘째, 차이의 "모양"만 기록함.**

> "It was important to us to do this in a way that protected user privacy."

요청·응답 본문을 저장하지 않고 **어느 단계인지, 프롬프트의 어느 조각인지, 처음 갈리는 바이트 위치, 두 버전의 바이트 길이**만 남겼음. 이 지문이 그대로 작업 단위가 됨. 조정 역할 에이전트가 **새로운 종류의 지문 하나마다 워커 에이전트 하나를 배정**했음.

실제로 잡힌 차이의 예가 **JSON 툴 호출의 이스케이프**임. Python 은 특정 문자를 이스케이프하는데 Rust 는 안 해서 프롬프트가 몇 바이트 갈렸음. 테스트로는 영원히 안 잡히고, 바이트 단위 대조로는 즉시 잡히는 종류임.

## 98% 대 24%

이 글에서 한 줄만 가져간다면 이것임.

| 시점 | 신호 | 값 |
|---|---|---|
| 4월 | 테스트 통과율 | 약 **98%** |
| 4월 말 | 프로덕션 입력 일치율 | **24%** |
| 5월 초 | 프로덕션 입력 일치율 | **6.5%** |
| 8월 | 프로덕션 입력 일치율 | **99.6%** |

일치율이 먼저 **떨어진** 것이 중요함. 비교 대상이 자사 트래픽에서 더 넓은 표본으로 옮겨가면서 덮이지 않았던 경로가 드러난 것이고, 중간의 하락 둘은 Rust 쪽 변경이 만든 것임. **검증기를 좋게 만들면 점수는 내려감.** 올라가는 점수를 성과로 보고하는 루프를 돌리고 있으면 이 단계에서 루프가 거짓말을 함.

반대로 프로덕션 신호에는 테스트에 없는 편향이 있음. 원문이 직접 적음. **흔한 버그 하나가 수많은 불일치를 만들기 때문에** 일치율은 버그 개수가 아니라 트래픽 가중치를 반영함. 그래서 두 신호는 교체 관계가 아니라 **가중치가 다른 두 신호**로 봐야 함.

## 세 루프, 사람이 들어가는 자리

| 루프 | 도는 속도 | 하는 일 | 사람의 자리 |
|---|---|---|---|
| inner | **1초 미만** | 에이전트가 두 코드베이스와 로컬 검사가 들어간 클라우드 샌드박스에서 차이를 고치고 테스트를 추가 | 없음 |
| outer | 배포 주기 | 사람 PR 리뷰 뒤 프로덕션 배포, 섀도 트래픽에서 해당 지문이 사라졌는지 확인 | PR 리뷰 |
| memory | 누적 | 엔지니어 교정이 `CLAUDE.md` 규칙, 반복 실수용 조회 노트, 영구 테스트와 린트로 굳음 | 규칙 승인 |

memory 루프의 구성이 구체적임. **Rust 가 Python 에서 드리프트하면 실패하는 테스트**, **리뷰어가 반복해서 지적한 패턴을 금지하는 린트**, 그리고 **Python 을 고치면 Rust 에 대응 변경을 하거나 면제를 요청해야 하는 머지 검사**. 마지막 것이 "목표가 움직였음" 문제를 조직 규칙으로 막은 것임.

6월에는 **에이전트가 팀의 리뷰 코멘트 약 60건을 훑어** 반복되는 문제를 묶고 규칙을 제안했고, 엔지니어가 그것을 고쳐 승인했음. 리뷰 코멘트를 메모리의 입력으로 쓴 것인데, [Memory Engineer](./2026-08-02-memory-engineer.md)가 "무엇을 버릴까"로 접근한 것과 방향이 반대임. 여기서는 **사람이 이미 말한 것 중 반복된 것만 남기는 쪽**이 선별 기준임.

## 검증기가 답하지 못하는 것

이 글이 스스로 그어 둔 선이고, 가장 실무적인 부분임.

> "A verifier can tell an agent whether the outputs matched, but not whether the fix is good enough to ship."

사례 둘.

**5월 중순, 웹 검색 툴 설명.** 프로덕션은 웹 검색 툴 설명을 내부 서비스에서 받아 오는데 Rust 쪽은 아직 그 서비스를 호출하지 않아 프롬프트에서 설명이 빠져 있었음. 에이전트는 그 텍스트를 Rust 가 읽을 수 있는 파일에 복사해 넣었고, **프롬프트는 일치했고 로컬 검증기를 통과했음.** 엔지니어가 거부함. 출시 전에는 그 서비스를 실제로 호출해야 하니 버릴 코드라는 것. **검증기를 만족시키는 가장 싼 경로가 설계를 무너뜨리는 경로일 수 있음.**

**추측에 의존한 이식.** 에이전트가 Python 의 동작을 추측한 일이 있고, 그래서 **"port exactly what Python did"** 가 규칙이 됨. 그 규칙으로 기존 코드를 다시 훑자 **추측에 의존한 자리가 7군데 더** 나왔음. 규칙 하나가 소급 감사 도구가 된 셈이고, 이것이 memory 루프가 inner 루프보다 값이 큰 이유임.

## 결과와 그 수치의 범위

| 지표 | 변화 | 측정 범위(원문이 밝힌 것) |
|---|---|---|
| 요청당 CPU | 약 **70% 감소** | 리전 **한 곳** |
| 요청당 메모리 | **80% 이상 감소** | 프로덕션 전체 |
| 중간값 TTFT | 약 **20% 감소** | **Claude Code 요청**, 더 짧은 기간 |

세 수치의 측정 범위가 서로 다름을 원문이 각 그림에 적어 뒀음. 그대로 인용할 때 **"API 가 전반적으로 20% 빨라졌다"로 옮기면 틀림.** TTFT 숫자는 Claude Code 요청 기준임.

작업량 쪽은 Rust 코드에 머지된 변경이 **4월 2주 구간 100건 미만에서 8월 10일 시작 구간 3,000건 이상**으로 올라갔음. 다만 원문이 그 그림에 **"Not all of them are migration work"** 라고 달아 둬서 이 수치는 이식 작업량의 상한으로만 읽어야 함. **2026년 5월 기준으로 Anthropic 이 머지하는 코드의 80% 이상을 Claude 가 쓰고 있다**는 서술도 같은 글에 있음.

## iOS 쪽에 남는 것

레거시 교체를 에이전트로 돌릴 때 그대로 옮겨지는 것 셋임.

1. **기존 구현을 검증기로 쓸 수 있으면 테스트를 늘리지 말 것.** Objective-C 를 Swift 로, UIKit 화면을 SwiftUI 로 옮기는 작업은 구 구현이 아직 돌고 있음. 두 구현에 같은 입력을 넣고 **출력의 바이트/스냅샷 차이**를 신호로 쓰는 쪽이 조합 테스트를 쓰는 쪽보다 싸게 넓음. [Evaluations 프레임워크](./2026-09-22-apple-evaluations-framework.md)와 [App Intents 테스트 경로](./2026-10-05-app-intents-testing-and-onscreen-context.md)가 이 자리에 쓰는 도구임
2. **비결정성을 비교에서 빼는 장치가 먼저임.** 모델 출력을 한 번만 받아 재생한 것이 이 글의 전제고, 온디바이스 모델을 쓰는 앱에서도 같음. 샘플링을 고정하거나 출력을 고정 재생하지 않으면 diff 가 전부 노이즈가 됨
3. **신호는 "어디서 갈렸는지"까지 가리켜야 함.** "다름"만 주는 검사로는 에이전트가 작업을 나눌 수 없음. 지문의 입도가 곧 병렬화 단위임

반대로 **그대로 가져오면 안 되는 것**은 섀도 트래픽 자체임. 앱 쪽에는 사용자 요청을 두 구현에 흘릴 서버 경로가 없는 경우가 많고, 사용자 데이터를 재생 대상으로 쓰는 것은 그 자체로 개인정보 설계 문제임. 원문이 본문을 저장하지 않고 **차이의 모양만** 남긴 이유가 그것임.

## 짚어야 할 것

- **이 글은 공개 제품 변경이 아님.** 사용자가 설정할 것도, API 표면이 바뀐 것도 없음. 읽을 값어치는 방법론이고, 수치는 Anthropic 내부 환경 기준임
- **TTFT 약 20% 는 Claude Code 요청 기준이고 기간도 더 짧음.** CPU 는 리전 한 곳, 메모리는 프로덕션 전체. 세 수치를 같은 범위로 묶어 인용하면 틀림
- **그림에서 읽은 수치가 섞여 있음.** 일치율 24% / 6.5% / 99.6% 와 2주당 머지 건수는 차트와 캡션에서 온 것이고, 원문이 캡션에 **"six misleading days are left out"** 이라고 적어 뒀음. 체크포인트 예시는 **made-up values**, 지문 점은 **illustrative** 로 표시돼 있음
- **에이전트 수와 모델을 확인할 수 없었음.** 병렬로 몇 개가 돌았는지 원문이 적지 않고, 루프 도구로 Claude Code 나 Managed Agents 를 지목하지도 않음. Claude Code 는 API 로 트래픽을 보내는 앱 쪽으로만 등장함
- **검색 쪽에 떠도는 수치와 다름.** 2차 보도 수준에서 CPU 40~50%, TTFT 10~20% 로 적는 글이 있는데 **원문으로 확인되지 않는 값**이고, 어느 측정 구간을 말하는지도 확인할 수 없었음. 인용할 때는 위 표의 범위와 함께 원문 수치를 쓸 것
- **원문의 교훈 절은 독자에게 명령형으로 적혀 있음**("Carefully design the verification signal", "Move toward outer loops"). 기사 조언 문체이고, 페이지에서 AI 에이전트를 겨냥한 지시문은 찾지 못했음

## 유효기간

**2026-11-27 확인 기준이고 글은 2026-11-25 발행임.** 이식 기록과 수치는 시점이 박힌 기록이라 낡지 않음. 낡는 것은 둘임. **섀도 비교를 만들어 주는 도구가 공개되는지**(이 글 시점에는 사내 구성 서술뿐임), 그리고 **같은 팀의 후속 글이 outer 루프 쪽 비중을 수치로 적는지**. 시작점은 [Anthropic Engineering](https://www.anthropic.com/engineering) 목록임.
