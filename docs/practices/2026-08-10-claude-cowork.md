## 요약

공식 문서 기준 Cowork 사용법임. 한 문장으로는 **터미널을 열지 않고 Claude Code와 같은 에이전틱 아키텍처를 쓰는 것**. 실무에서 알아야 할 축은 넷임. 반복 작업을 담는 **Projects**, 백그라운드로 돌리는 **Dispatch**, 안전을 가르는 **권한 3모드**, 그리고 능력을 늘리는 **플러그인**. 뒤쪽 절반은 커뮤니티 세팅 가이드(Ruben Hassid)를 붙이고, 공식 문서와 어긋나는 지점을 갈라 정리함. 실무에서 가장 값어치 하는 건 그쪽의 **토큰 절약 6가지**고, 그중 1번은 무조건이 아님.

## 무엇인가

프롬프트에 순차적으로 응답하는 대신, 복잡한 다단계 작업을 자율적으로 처리함. 결과물을 서술하고 자리를 떠난 뒤 완성된 작업으로 돌아오는 방식임.

핵심 능력 넷을 공식 문서가 이렇게 꼽음.

- **컴퓨터에서 직접 작동**: 수동 업로드·다운로드 없이 로컬 파일을 읽고 씀
- **Claude in Chrome 연동**: [Chrome](https://claude.com/chrome)과 짝지어 웹사이트 작업을 자동화
- **서브에이전트 조율**: 복잡한 작업을 작은 태스크로 쪼개 병렬 워크스트림으로 처리
- **완성된 산출물**: 수식이 동작하는 Excel, PowerPoint, 형식이 잡힌 문서

## 어디서 쓰나

| 항목 | 내용 |
|---|---|
| 플랜 | Pro, Max, Team, Enterprise (유료만) |
| 데스크톱 | macOS, Windows |
| 웹·모바일 | claude.ai, iOS·Android 최신 버전. Max·Team·Enterprise는 베타, Pro는 순차 적용 |
| 시작 | 메시지 박스에서 Chat 대신 **Cowork** 선택 |

세션은 Anthropic 클라우드에서 돌아서 기기를 넘어 지속됨. 다만 **"클라우드에서 돈다"와 "데스크톱 없이 끝까지 간다"는 다름.** 이 둘을 갈라야 함.

| 작업 성격 | 데스크톱을 닫아도 되나 |
|---|---|
| 클라우드 자원만 쓰는 작업 (웹 검색, 문서 작성, 데이터 정리) | 계속 진행됨 |
| **로컬 파일 접근, 브라우저 사용, 컴퓨터 제어가 필요한 작업** | ❌ 작업 내내 Claude Desktop을 열어둬야 함 |
| **Dispatch** | ❌ 데스크톱이 호스트라서 컴퓨터가 깨어 있고 온라인이어야 함 |

즉 세션 자체는 살아남지만, **로컬 자원에 의존하는 단계는 데스크톱이 없으면 진행되지 못함.** 마운트한 프로젝트 폴더를 읽거나 쓰는 작업이 여기 해당함.

## Projects, 반복 작업의 단위

여기가 공식 문서에서 가장 중요한 부분임. 반복되는 작업 영역에 필요한 것을 한 데 모음.

| 항목 | 용도 |
|---|---|
| Description | 프로젝트 용도. **Dispatch가 태스크에 맞는 프로젝트를 고를 때 읽음** |
| Folders | 이 프로젝트 세션에서 Claude가 읽고 쓸 로컬 폴더 |
| Instructions | 프로젝트의 모든 세션에 적용되는 상시 지침 |
| Links | Claude가 참조할 URL (문서, 대시보드, 저장소) |
| Projects from Chat | claude.ai에서 만든 프로젝트의 지식을 끌어옴 |
| Memory | **프로젝트 범위로 세션을 넘어 지속되는 메모리 저장소** |

**프로젝트는 내 컴퓨터에 있음.** 클라우드에 동기화되지 않고 다른 사람과 공유되지 않음.

### 만들기

좌측 **Projects**에서 `+`. 시작점 세 가지 중 고름.

- **Start from scratch**: 새 폴더로 빈 프로젝트
- **Import a project**: 기존 claude.ai 프로젝트를 Cowork로 가져옴
- **Use an existing folder**: 이미 작업하던 폴더를 가리킴

### 작동 방식

프로젝트를 고르면 그 폴더가 마운트되고 지침이 적용된 세션이 시작됨. Claude가 만든 파일은 프로젝트 폴더에 떨어지고, **세션 중 배운 것은 프로젝트 메모리에 저장돼 다음에 쓰임.**

파일이나 폴더를 프로젝트에 끌어다 놓으면, 개별 파일은 **첫 번째 폴더로 복사**되고 폴더는 **추가 프로젝트 폴더로 마운트**됨. 개별 파일은 **최대 50MB**까지 읽음.

### Cowork 프로젝트 ≠ claude.ai 프로젝트

| | Cowork 프로젝트 | claude.ai 프로젝트 |
|---|---|---|
| 위치 | 내 컴퓨터에만 | Claude 계정에 |
| 로컬 폴더 보유 | 가능 | 불가 |
| 팀 공유 | 불가 | 가능 (Team, Enterprise) |

claude.ai 프로젝트를 Cowork 프로젝트에 **링크**해서 지식을 끌어올 수 있음. 링크는 병합이 아니라 참조임.

### 보관

Archive는 프로젝트를 목록에서 없애고 메타데이터(이름, 지침, 링크, 메모리)를 삭제함. **붙여둔 로컬 폴더는 건드리지 않음.** 파일은 디스크에 그대로 남음.

## Dispatch, 백그라운드 위임

Pro 또는 Max 플랜과 최신 데스크톱 앱이 필요함. 고수준 지시를 받아 백그라운드에서 수행하는 장기 실행 에이전트임.

대화 하나에서 결과물을 서술하면, Dispatch가 그것을 태스크로 쪼개고 **각각을 별도 Cowork 또는 Code 세션으로** 실행한 뒤 사이드바에 결과를 올림. 일반 Cowork 채팅과 달리 각 단계를 지켜보지 않음.

### 라우팅

| 태스크 유형 | 실행 위치 | 예시 |
|---|---|---|
| 코딩 작업 | **Code**, 이미 설정한 워크스페이스에서 | 버그 수정, PR 열기, 테스트 실행 |
| 지식 작업 | **Cowork**, 지정한 프로젝트에서 (없으면 기본 프로젝트) | 리서치, 문서 작성, 파일 정리 |

어느 Code 워크스페이스나 Cowork 프로젝트를 쓸지 지정할 수 있고, 안 하면 목록을 보여주고 알아서 고름.

**Dispatch 에이전트는 하나지만 그 아래로 여러 자식 태스크를 돌림. 자식 태스크는 자기 자식을 만들지 않음.**

### 상태

Running, Awaiting input, Awaiting answer, Completed, Error, Archived. 아무 태스크나 선택하면 전체 트랜스크립트와 Claude가 밟은 단계, 만든 파일을 볼 수 있음.

### ⚠️ 승인 타임아웃 10분

자식 태스크가 권한이 필요하면 프롬프트가 나에게 전달됨. **10분 안에 응답하지 않으면 요청이 자동 거부되고 태스크는 그 행동 없이 계속 진행됨.** 자리를 비운 사이에 조용히 반쪽짜리 결과가 나올 수 있다는 뜻이라, 백그라운드 위임에서 가장 조심할 지점임.

### 폰에서 시키기

Claude Desktop이 돌고 있으면 내 컴퓨터가 Dispatch 호스트로 등록됨. 모바일 앱에서 Dispatch 대화를 시작하면 **작업은 데스크톱에서 돌고** 결과는 양쪽에서 확인 가능함. 데스크톱을 열어두고 컴퓨터가 깨어 있고 온라인이어야 함.

## 권한 3모드

안전이 갈리는 지점임.

| 모드 | 동작 | 비고 |
|---|---|---|
| **Manual** | 행동마다 멈추고 승인을 요청 | 기본적으로 가장 안전 |
| **Auto** | 자율 진행하되 데이터 유출·프롬프트 인젝션 같은 위협에 대해 안전 검사를 돌림. 불안전한 행동은 차단하고 대안을 찾거나 명시적 허가를 요청 | **Pro·Max 전용. 추가 검사 때문에 사용량을 더 씀** |
| **Skip** | 자동 정지 없음. 중단 없이 행동 | 관여하는 모든 행동·커넥터·파일·앱을 **완전히 신뢰할 때만** |

읽기 전용 툴(보기, 검색)은 대개 모드와 무관하게 자동 승인되고, 쓰기·삭제는 모드별 처리를 따름.

**삭제 보호.** 파일을 영구 삭제하기 전에는 명시적 허가가 필요함. 안전 프롬프트가 뜨고 Allow를 골라야 함.

**세션 격리.** 작업은 내 컴퓨터와 네트워크로부터 분리된 Anthropic 서버의 격리 환경에서 돎. 셸 명령과 코드가 그 샌드박스 안에서 실행됨. 다만 공식 문서도 명시함. **"Claude는 내가 허가한 로컬 파일에 접근하고 나를 대신해 실제 행동을 취할 수 있음. 진행을 허용하기 전에 계획된 행동을 검토할 것."**

## 스킬, 커넥터, 플러그인

사이드바 **Customize**에서 관리함. Cowork는 claude.ai 계정에 활성화된 것을 **세션 시작 시 동기화해서** 로드함.

⚠️ **Cowork는 Claude Code CLI의 `~/.claude` 디렉터리를 읽지 않음.** `~/.claude`에만 있는 스킬이나 플러그인을 쓰려면 Customize에서 따로 추가해야 함. Claude Code와 Cowork를 같이 쓰는 사람이 가장 자주 걸릴 함정임.

### 플러그인이 담을 수 있는 것

| 구성요소 | 추가되는 것 |
|---|---|
| Skills | 워크플로를 가르치는 재사용 지시 |
| Connectors | 외부 서비스에 접근하는 MCP 서버 |
| Agents | 위임 가능한 전문 서브에이전트 |
| Hooks | 세션의 정해진 지점에서 실행되는 스크립트 |

설치는 **Customize → Plugins**. 기본 마켓플레이스는 Anthropic 공식 카탈로그이고, URL로 다른 마켓플레이스를 추가할 수 있음. 파일 업로드도 가능함.

### Git 저장소를 마켓플레이스로

플러그인 패키지를 담은 Git 저장소를 마켓플레이스로 쓸 수 있음. **팀이 공개 카탈로그에 올리지 않고 자체 플러그인을 배포하는 전형적인 방법임.** GitHub(Enterprise 포함) 지원, GitLab과 Bitbucket은 공개 저장소만. `https://github.com/owner/repo` 또는 `owner/repo` 축약형을 받음.

### 한도

| 항목 | 값 |
|---|---|
| 플러그인 패키지 크기(비압축) | 200 MB |
| 패키지당 파일 수 | 5,000 |
| 마켓플레이스 저장소 아카이브 | 512 MB |
| 마켓플레이스당 플러그인 | 500 |
| 추가 가능한 마켓플레이스 | 25 |
| 인앱 스킬 뷰어 미리보기 | 파일당 1 MB |

1MB를 넘는 파일은 목록에 "too large to preview"로 뜨지만 런타임에는 Claude가 쓸 수 있음.

Team·Enterprise에서는 관리자가 특정 플러그인을 전원에게 필수로 지정할 수 있고, 그건 사용자가 제거할 수 없음.

## 장기 실행과 스케줄

**고정된 단일 컨텍스트 한계를 넘어 장기 실행할 수 있음.** 대화 타임아웃으로 끊기지 않는다는 뜻이고, 사용량 한도·오류·권한 거부·종료 조건은 그대로 있음.

스케줄 태스크는 `/schedule` 명령이나 Scheduled 사이드바로 만듦. 온디맨드로도, 정한 주기로도 실행됨.

공식 문서는 **"클라우드에서 돌아서 기기가 깨어 있거나 앱이 열려 있지 않아도 된다"**고 씀. 다만 이 문장은 위의 지속성 항목과 같은 단서를 달아야 함. 프로젝트 안에서 만든 스케줄은 **마운트된 폴더, 로컬 MCP 플러그인, 브라우저·컴퓨터 접근에 의존**할 수 있고, 같은 문서가 그런 자원에는 데스크톱이 열려 있어야 한다고 말함.

- 클라우드 자원만 쓰는 스케줄(웹 검색, 요약, 리포트 작성)이면 문서 설명대로 기기와 무관하게 돎
- **로컬 자원에 의존하는 스케줄은 데스크톱이 꺼져 있으면 그 단계를 수행할 수 없음**
- ⚠️ 이때 스케줄 생성 시점에 거부되는지, 실행 시점에 실패하는지, 그 단계만 건너뛰는지는 **공식 문서에 없고 제가 확인하지 못했음.** 로컬 폴더를 건드리는 스케줄을 걸 거라면 한 번 돌려보고 결과를 확인하는 편이 안전함

## 사용량

Cowork는 일반 채팅보다 사용량을 더 씀. 복잡한 다단계 작업이 연산 집약적이고 토큰을 더 필요로 하기 때문. **Auto 모드는 안전 검사 때문에 추가로 더 씀.**

공식 문서가 권하는 절약 전략 셋.

- 관련된 작업을 묶어서 처리
- 단순한 일은 일반 채팅으로
- Settings → Usage에서 사용량 모니터링

## 현재 한계

- **Chat의 메모리가 Cowork 세션으로 넘어오지 않음.** 프로젝트는 Cowork 안에서 메모리를 지원함
- **세션을 다른 사람과 공유할 수 없음**
- 라이브 artifacts와 로컬 MCP 플러그인 같은 일부 기능은 Claude Desktop이 필요함
- 프로젝트 범위를 벗어난 세션 간 메모리 지속성은 아직 없음

## 커뮤니티 세팅 가이드

Cowork 가이드로 2천만 조회를 받은 Ruben Hassid가 **"내 예전 글을 읽지 마라"**로 시작하는 글임. 파일과 폴더 중심 세팅이 기업 현장에서 깨졌고, 대신 **Skills + Projects 두 개만** 쓰라는 게 결론. 공식 문서와 갈리는 지점은 다음 절에서 따로 짚음.

### 왜 예전 방식을 버렸나

저자는 원래 "파일과 폴더" 전도사였음. LinkedIn 절반이 자기 때문에 그렇게 쓰고 있다고 인정함. 그런데 수백 명 규모 기업에 워크숍을 다니면서 그 시스템이 깨졌음. 이유는 둘.

- **폴더가 샌다.** "내 output 폴더 절대 확인하지 마"라고 해도 Claude가 종종 확인함. 그러면 낡은 출력이 컨텍스트를 오염시킴
- **파일 유지가 불가능하다.** 본업이 있는 사람이 매주 몇 시간씩 "about-me" 파일을 갱신할 수 없음. 처음엔 좋았다가 고통스러운 병목이 됨

저자의 다른 주장 하나도 흥미로움. **AI에 지시를 너무 많이 주면 안 됨.** 컨텍스트를 과하게 주면 매번 똑같은 답만 나오고 창의성이 사라짐. 같은 계약서를 반복 작성할 때는 괜찮지만, 브레인스토밍에는 안 맞음.

### Skills와 Projects 구분

| | Skills | Projects |
|---|---|---|
| 정체 | **호출하는 능력** | **찾아가는 장소** |
| 이동성 | 어느 채팅에나 따라감. Gemini, ChatGPT 같은 다른 AI에도 감 | 그 안에 머묾 |
| 내용 | 슬래시 명령으로 호출 (`/linkedin-post`) | 저자 표현으로는 "파일 + 지시가 계속 로드되고 기억함", 팀과 공유 가능 |

**구분 기준이 단순함.**

> 남에게 가르칠 수 있는 기술이면 → Skill
> 특정 맥락(고객, 캠페인)이면 → Project

팀에 이 차이를 가르쳐야 함. 안 그러면 몇 개 Project로 끝날 게 수백 개 Skill이 되거나, 공유 Skill이어야 할 게 수십 개 Project가 됨.

⚠️ 표의 "파일 + 지시가 계속 로드됨"과 "프로젝트 안의 모든 채팅이 그 프로젝트 전체 컨텍스트를 가진다"는 저자 표현으로 읽어야 함. 위 [Projects](#projects-반복-작업의-단위) 절이 설명하는 실제 동작은 **폴더 마운트와 공통 Instructions, 프로젝트 범위 Memory**이고, 과거 채팅 전체가 매 세션의 모델 컨텍스트에 주입된다는 얘기가 아님. 폴더가 **접근 가능하게 마운트되는 것**과 파일 전부가 매 호출 컨텍스트에 들어가는 것은 다름.

**스킬 만드는 방법 세 가지**

- Claude의 `/skill-creator`로 질문에 답하며 만들기
- 저자가 만든 무료 도구 `makemyskill.com`
- 진행 중인 채팅 상단의 대화 이름을 클릭 → "Turn into skill"

**팀 공유의 함정.** Projects를 공유하려면 Cowork가 아니라 **Chat에서** 만들어야 함. 만든 뒤 오른쪽 위에서 공유 설정하고, 그다음 Cowork로 작업을 시작함. 저자도 "이상한 거 안다"고 씀.

**아직 불편한 점 둘.** 스킬이 설명(description)만으로 자동 발동함. 저자는 호출할 때만 켜지길 원하는데 끌 수 없음. 그리고 Projects에 업로드 가능한 파일 수 제한이 있음.

### AskUserQuestion 트릭

저자가 자기 최고의 트릭이라고 부르는 것. 프롬프트를 잘 못 쓰는 문제 대부분을 이걸로 해결함.

```text
I need to [작업, 예: "write a PR brief for the launch of my company"]
for [성공 기준, 예: "to get more leads"].
First, use the tool AskUserQuestion to get more info.
```

Claude가 답만 하면 되는 폼을 만들어줌. 답하고 나면 Claude가 어떻게 답할지 더 깊이 생각함. 첫 프롬프트만이 아니라 **계속 이어서 쓸 수 있음.** 실패가 불가능할 만큼 컨텍스트를 줄 때까지 Claude가 계속 인터뷰함.

### 병목은 사람이다

전형적인 Cowork 세션을 저자가 초 단위로 쪼갬. 프롬프트 타이핑 30초, Cowork가 스킬 읽기 50초, 계획 생성 50초, AskUserQuestion으로 질문 50초. 그다음 사람이 답함. 커스텀 답변은 **하나당 60초~2분.** 질문 8개면 **8~15분 동안 사람이 느린 부분**임.

> Cowork는 15초에 10만 단어를 읽고 90초에 스프레드시트를 만듦. 그런데 분당 60단어로 타이핑하는 사람을 기다려야 함. 사람은 분당 150단어로 말할 수 있음.

그래서 받아쓰기 도구를 씀. 속도만이 아니라 **말할 때 훨씬 많은 컨텍스트를 주기 때문**임. 저자는 세 곳에서 말로 함. 최초 프롬프트, AskUserQuestion 답변 중 컨텍스트가 필요한 것, 그리고 피드백과 방향 전환. 타이핑하던 "톤이 틀렸어, 덜 격식적으로"가 말로는 "톤이 너무 딱딱해. 200명 회사를 운영하는 친구한테 문자 보내는 느낌이었으면 해. 데이터는 두고 캐주얼하게. 2번 섹션만 다시"가 됨.

### 토큰 절약 6가지

**1. 후속 메시지 대신 대화를 재시작함.** Claude는 메시지를 세지 않고 토큰을 셈. 메시지를 보낼 때마다 **전체 대화 히스토리를 다시 읽음.** 저자는 30번째 메시지가 1번째보다 **31배** 비싸다고 씀. 교환당 약 500토큰이면 20메시지에 105K, 30메시지에 232K를 태운다는 계산도 같이 제시함. 방법은 "아니 내 말은..."을 보내지 말고 이전 메시지에서 **"Restart the conversation from here"**를 누르거나 자기 프롬프트를 편집하는 것.

⚠️ 위 두 수치가 서로 안 맞음. 교환당 500토큰이면 1번째 요청의 입력은 500, 30번째는 15,000이라 **30배**임. 누적 232,500토큰은 저자가 말한 232K와 맞으니 누적 계산은 성립함. **배수를 그대로 인용하기보다 "히스토리가 선형으로 쌓인다"는 방향만 취하는 게 안전함.** 이 항목이 언제 이득인지는 다음 절에서 캐시를 넣고 다시 따짐.

**2. 20메시지마다 새 세션.** 긴 대화는 토큰 화로임. 한 개발자가 자기 사용량을 추적했더니 **98.5%가 히스토리 재독에 쓰이고 실제 출력은 1.5%**였음. 세션이 길어지면 Claude에게 요약을 `.md`로 만들게 하고, 새 세션의 첫 메시지로 붙여넣음.

**3. 작업을 한 메시지로 묶음.** 프롬프트 3개 = 컨텍스트 3번 재로드. 한 프롬프트에 3개 작업 = 1번 재로드.

**4. 빠른 작업엔 Opus 대신 Sonnet.** 문법 검사, 브레인스토밍, 서식, 짧은 답변. 기술적으로는 Haiku가 더 쌈. 초안과 단순 작업을 Sonnet·Haiku로 돌리면 **예산의 30~70%**가 깊은 작업용으로 남음.

**5. ABOUT ME 파일을 지움.** 버리는 게 아니라 **스킬로 바꿈.** 그러면 원할 때만 호출함.

**6. 하루에 걸쳐 분산함.** Claude는 5시간 롤링 윈도우를 씀. 아침 세션에 한도를 다 태우면 하루 용량 대부분이 안 쓰이고 남음. 아침·오후·저녁 2~3세션으로 쪼개고, 평일 태평양시 **오전 5~11시 피크**를 피함. 저자 본인은 "이론상 멋지지만 실제로 안 한다"고 솔직히 씀.

**1~3번은 Cowork 전용 원리가 아니라 대화형 LLM 전반에 통함.** 반면 4번(모델 선택), 5번(스킬), 6번(5시간 롤링 윈도우)은 특정 제품·플랜 기능이라 그대로 옮겨지지 않음.

### 첫 20분

- 0~3분: 설정 비우고 전부 끔
- 3~8분: 계속 하는 일로 첫 Skill 만들기
- 8~13분: 첫 Project 만들기 (고객 PDF, 엑셀 업로드)
- 13~17분: 프로젝트 안에서 스킬을 써보며 감 잡기
- 17~20분: 저자의 스킬 라이브러리 받기

### 이 글을 읽을 때

- **자기 홍보가 매우 많은 글임.** 유료 도구, 뉴스레터, 컨설팅, 추천 링크가 본문에 계속 나옴. 걸러 읽어야 함
- **개발자가 아닌 사람**을 대상으로 쓴 글임. 코드가 산출물이면 Claude Code를 쓰라고 저자도 명시함
- "AI에 컨텍스트를 너무 주면 창의성이 죽는다"는 주장은 검증된 게 아니라 저자 경험임. 다만 [Prompt Caching](../agents/2026-07-22-prompt-caching-in-agents.md) 관점에서 보면 시스템 프롬프트를 가볍게 유지하는 건 비용 면에서도 이득임
- Cowork 세부 UI 설명은 원문 스크린샷에 의존하는 부분이 많아서 여기 다 옮기지 않았음

## 공식 문서와 어긋나는 지점

위 커뮤니티 가이드와 공식 문서가 정면으로 갈리는 부분이 있음.

**"폴더를 버려라" 대 Projects 중심 설계.** 저자는 폴더가 새고 파일 유지가 불가능하다며 폴더를 버리고 Skills + Projects만 쓰라고 함. 그런데 공식 문서의 Projects는 **로컬 폴더를 붙이는 것이 핵심 기능**임. Dispatch도 프로젝트 폴더로 라우팅함.

읽어보면 둘이 완전히 모순은 아님. 저자가 비판한 건 **직접 관리하는 임의의 폴더 구조와 수동 유지가 필요한 about-me 파일**이고, 공식 Projects는 폴더를 붙이되 **지침과 메모리를 시스템이 관리**함. "about-me 파일을 스킬로 바꿔라"는 조언은 공식 구조에서는 프로젝트 Instructions와 Memory가 대신하는 셈임.

**"설정을 다 끄는 게 최선"이라는 주장.** 저자는 Global Instructions를 비우라고 하는데, 공식 문서는 톤·형식·역할을 Global Instructions에 두라고 안내함. 컨텍스트를 많이 주면 창의성이 죽는다는 건 저자의 경험이고 공식 입장이 아님. 브레인스토밍과 반복 문서 작성에 서로 다른 세팅을 쓰는 게 실용적일 것으로 보임.

**토큰 절약 6가지는 대체로 유효하지만 1번은 무조건이 아님.** "후속 메시지 대신 대화 재시작"이 항상 이득이라고 읽으면 틀림.

"30번째 메시지가 1번째보다 31배 비싸다"는 계산은 **캐시를 빼고 센 것**임. 캐시가 살아 있으면 그 히스토리 재독은 정상 input이 아니라 할인된 cache-read로 청구됨. 그리고 [Prompt Caching](../agents/2026-07-22-prompt-caching-in-agents.md)이 지적하듯 **rewind와 fork는 토큰 시퀀스를 바꾸는 행위**이고, 히스토리를 재작성하는 즉시 비용이 미래 절약분을 넘을 수 있음.

정확히 따지면 이렇게 갈림.

- **앞 지점으로 truncate하면 그 지점까지의 prefix는 살아남음.** 캐시는 prefix 단위라, 30번째에서 5번째로 되돌리면 1~5번은 여전히 히트할 수 있음
- **이미 지불한 suffix 쓰기 비용은 매몰 비용임.** 앞으로의 비교에서 빠짐. 버리는 게 아까워서 이어붙인다는 판단은 성립하지 않음
- 그래서 **입력 비용만 보면 남은 턴이 하나여도 truncate가 같거나 쌈.** 이어붙이면 매 턴 suffix 전체가 cache-read로 다시 붙고, truncate하면 짧아진 prefix만 읽음
- 이어붙이는 게 싼 경우는 조건이 붙음. **되돌릴 지점에 캐시 블록이 없을 때**임. 그러면 짧아진 prefix를 read가 아니라 write로 다시 올려야 해서 오히려 비쌀 수 있음

숫자를 넣으면 이렇게 갈림. 캐시 read는 기본 input의 **0.1배**, write는 **1.25배**(5분 TTL)로 청구됨.
prefix 5k, suffix 25k에 한 턴을 더 주고받는 상황을 잡으면,

| 선택 | 입력 비용 (기본 input 환산) |
|---|---|
| 이어붙이기 | 30k × 0.1 = **3k** |
| truncate, 되돌릴 지점 캐시 히트 | 5k × 0.1 = **0.5k** |
| truncate, 그 지점 캐시 없음 | 5k × 1.25 = **6.25k** |

정리하면 판단 기준은 **되돌릴 지점에 캐시가 살아 있는지**임. 살아 있으면 남은 턴 수와 무관하게
truncate가 싸고, 없으면 이어붙이는 편이 나음. 남은 턴 수는 여기서 결정 변수가 아님.

**단, 토큰 비용 밖의 비용이 따로 있음.** 버린 suffix에 있던 맥락을 다시 설명해야 하거나 모델이
한 작업을 다시 하게 되면 그쪽이 더 비쌈. 마무리 단계에서 이어붙이는 편이 낫다는 감각은 대개
토큰 비용이 아니라 이 정보 손실에서 옴.

나머지 5가지도 단서가 아예 없는 건 아님.

| 항목 | 단서 |
|---|---|
| 작업 묶기 | 조건 없음. 공식 문서가 권하는 "관련 작업 묶기"와 같은 방향 |
| 20메시지마다 새 세션 | 요약으로 옮기는 과정에서 정보가 빠짐. 캐시가 뜨거운 구간이면 손해일 수 있음 |
| 빠른 일은 Sonnet | 제품이 모델 선택을 열어줘야 성립 |
| ABOUT ME를 스킬로 | 스킬 로스터가 prefix에 들어가므로 세션 시작 시 고정돼 있어야 이득 |
| 하루에 분산 | **5시간 롤링 윈도우가 있는 플랜에만 해당** |

## 실무 메모

- **Claude Code를 이미 쓰고 있으면 `~/.claude`가 공유되지 않는다는 점을 먼저 확인할 것.** 스킬을 두 곳에 따로 등록해야 함
- **Dispatch의 10분 승인 타임아웃**을 모르고 자리를 비우면 반쪽 결과가 나옴. 백그라운드로 돌릴 작업은 승인이 필요 없게 프로젝트 폴더와 권한을 미리 맞춰두는 편이 나음
- **Auto 모드는 더 안전한 대신 사용량을 더 씀.** 신뢰 수준과 비용을 같이 놓고 골라야 함
- 팀 배포라면 **Git 저장소를 마켓플레이스로 쓰는 방법**이 핵심임. 공개 카탈로그에 올리지 않고 사내 플러그인을 배포하는 표준 경로
