## 요약

한 사람은 Claude에 최신 전략을 브리핑하고, 다른 사람은 Codex한테 옛 폴더를 뒤지게 하고, 세 번째 사람은 쓸 만했던 워크플로를 기억으로 다시 만듦. **모든 대화가 조금씩 다른 버전의 회사를 들고 있음.** 이 글의 진단이 그것이고, 처방은 모델 아래에 공유 계층을 하나 깔자는 것임.

핵심 주장은 한 줄로 압축됨. **모델이 지능을 공급하고, 하네스가 회사를 공급함.** 같은 모델이 회사마다 다르게 느껴지는 이유는 모델이 아니라 작업 환경이라는 것. [Harness · Loop · Graph](../practices/2026-07-28-loop-graph-harness.md)의 harness 계층을 개인이 아니라 **팀 단위로** 세우는 구체적 절차로 읽으면 값어치가 있음.

## 하네스가 답해야 하는 다섯 가지 질문

긴 시스템 프롬프트로도 한 세션 동안은 답할 수 있음. 회사 하네스는 그 답을 **구조화하고, 지속시키고, 전원에게 준다**는 게 차이임.

1. AI가 무엇을 아는가
2. 관련 맥락을 어떻게 찾는가
3. 어떤 규칙을 지켜야 하는가
4. 어떤 반복 작업을 수행할 수 있는가
5. 각 실행이 다음 실행을 어떻게 개선하는가

지식은 검색 가능해지고, 규칙은 대화가 끝나도 남고, 툴에는 경계가 생기고, 작업은 산출물을 남기고, 승인된 워크플로는 재사용 가능해짐.

## 회사 전체를 먼저 그리지 말 것

이 글에서 제일 실용적인 부분임. 회사 전체를 모델링하려 들면 **정리된 맥락 몇 주치와 개선 증거 0건**으로 끝날 수 있음. 워크플로 하나로 먼저 증명하라는 것.

고를 워크플로의 네 가지 속성.

- 자주 일어남
- 경계가 분명함
- 회사 맥락에 의존함
- 사람이 결과를 빨리 판정할 수 있음

예시로 든 건 **주간 인텔리전스 브리프**임. 입력은 이미 존재하는데 회의록·프로젝트 파일·결정·사람들 머릿속에 흩어져 있고, 출력은 팀 전체에 쓸모 있고, 창업자가 정확한지 금방 판단할 수 있음.

워커를 만들기 전에 계약부터 정의함.

| 항목 | 내용 |
|---|---|
| **입력** | 최근 7일 회의, 현재 프로젝트 상태, 결정·약속·미결 질문, 리스크와 막힌 작업 |
| **처리** | 출처 검색 → 사실 주장 검증 → 모순과 누락 표면화 → 회사 수준 변화 종합 |
| **출력** | 내린 결정, 프로젝트별 진행, 리스크와 블로커, 다음 주 약속, 출처 목록 |
| **경계** | 초안까지만. 배포 전 사람 검토에서 멈춤 |

> 사람이 돌릴 때마다 절차가 매번 바뀐다면 아직 수동으로 두라는 단서가 붙음. **반복 가능해진 다음에 공유 인프라가 되는 것**이지 그 반대가 아님.

## 기억 — 전부 밀어넣지 않고 지도를 준다

설치는 한 줄임.

```
npx create-hq
```

그다음 주간 브리프에 필요한 맥락만 넣음. 글이 제시하는 최소 구조는 이렇게 생겼음.

```
HQ/companies/your-company/
  company-brief.md
  knowledge/     결정과 플레이북
  sources/       회의
  signals/
  people/
  projects/
  policies/      weekly-intelligence.md
  workers/       weekly-intelligence
```

여기서 캐싱 관점으로 중요한 문장이 나옴. **회사 전체를 모든 프롬프트에 주입하지 않음.** HQ의 charter가 지식·정책·프로젝트·워커가 어디 있는지 **지도**만 주고, 에이전트가 그 지도를 따라 필요한 깊은 출처를 꺼내 옴.

> 에이전트에게 작고 안정적인 진입점을 주고, 깊은 맥락은 필요할 때 꺼내게 하라.

작업이 시작되기도 전에 컨텍스트 윈도를 다 쓰는 걸 막는 설계임. [Prompt Caching In Agents](./2026-07-22-prompt-caching-in-agents.md)의 관점에서 보면 **안정적인 진입점을 prefix에 두는 것**과 같은 방향이고, [Memory Engineer](../practices/2026-08-02-memory-engineer.md)가 지적한 "원시 메모리를 더 주면 오히려 나빠질 수 있음"에 대한 대응이기도 함.

## 정책 — 통제의 세 층위

지식은 무슨 일이 있었는지 알려주고, 정책은 그 일을 회사가 **어떻게 다루길 기대하는지** 알려줌. 주간 인텔리전스 정책 예시가 여섯 줄임.

1. 모든 사실 주장에 출처를 붙일 것
2. 모순되는 증거를 표면화할 것. 조용히 해소하지 말 것
3. 리스크는 출처의 원래 긴급도 그대로 보고할 것
4. 누락·오래됨·불확실한 정보에 라벨을 붙일 것
5. 시크릿이나 타사 맥락을 절대 포함하지 말 것
6. 배포 전 사람 승인에서 멈출 것

여기서 이 글의 가장 이식성 높은 구분이 나옴.

| 층위 | 성격 | 예시 |
|---|---|---|
| **instruction** | 선호를 따라달라고 요청 | 그때그때의 지시 |
| **policy** | 세션과 사람을 넘어 지속되는 규칙 | "출처를 붙여라" |
| **hook / 기계적 검사** | 실패 비용이 크면 행동 자체를 차단 | "승인 없이 절대 발송 금지" |

가능한 모든 동작을 기술하려 들지 말고 **모델·팀원·프로젝트가 바뀌어도 살아남아야 할 불변항 몇 개만** 인코딩하라는 게 요점임. 첫 정책은 사람들이 유지보수할 만큼 짧게 유지할 것.

## 워커 — 좁은 직무 하나

승인된 절차를 재사용 가능한 워커로 만드는 단계임. `/newworker` 로 만들되 **직무를 하나로 좁히라**고 함. "회사 분석가"는 그럴듯하지만 테스트하기 어렵고 오용하기 쉬움.

워커 명세에 `Never` 항목이 따로 있는 게 눈에 걸림 — 없는 사실 지어내지 않기, 다른 회사 맥락 읽지 않기, 시크릿 노출하지 않기, 브리프를 발송·게시하지 않기. 그리고 완료 조건이 **"모든 주장이 뒷받침되거나 불확실로 라벨링됐고 사람 검토 준비가 됐을 때"** 로 정의됨.

> 회사 지식이 사실을 공급하고, 정책이 판단을 공급하고, 워커가 반복 가능한 순서를 공급함.
> 프롬프트 하나는 쓸 만한 브리프 하나를 만들지만, 워커는 그 방법을 **다음 주 금요일 다른 팀원**이 쓸 수 있게 함.

## 수정을 프롬프트가 아니라 층에 넣기

이 글에서 제일 건질 게 많은 표임. 첫 성공 실행을 완성된 인프라로 취급하지 말고, 수정 하나하나를 **맞는 층에서** 진단하라는 것.

| 증상 | 고쳐야 할 층 |
|---|---|
| 사실이 빠짐 | 회사 지식 |
| 엉뚱한 맥락을 가져옴 | 라우팅과 리소스 설명 |
| 같은 실수를 반복함 | 워커 스킬 |
| 위험한 동작 | 정책 또는 hook |
| 산출물이 약함 | 출력 계약 |
| 정보가 오래됨 | 지식 가드닝 |

회의가 애초에 기록되지 않아서 워커가 결정을 놓쳤다면 프롬프트를 다시 쓰는 걸로는 시스템이 안 고쳐짐. 지식 경로를 고쳐야 함. 리스크를 사소한 업데이트 아래 계속 묻는다면 출력 계약을 날카롭게 해야 함.

> 쓸모 있는 질문은 **"환경의 어느 부분이 이 실수를 허용했나"** 임.

## `/hq-sync` — 한 사람의 개선이 팀 기본값이 되는 지점

브리프·정책·워커가 검토를 통과하면 `/hq-sync` 로 Main에 합침. 영업은 반론 대응을 스킬로, 지원은 에스컬레이션 규칙을, 운영은 리포트 개선을, 엔지니어링은 리뷰 게이트를 얹음. 다음 팀원은 원래 대화나 프롬프트 없이 개선된 버전에서 시작함.

다만 저자 본인이 같은 절에서 경고를 답. **공유 학습은 판돈도 같이 올림.** 약한 지시 하나가 이제 전원에게 영향을 주므로 Main을 프로덕션처럼 다루라고 함. 회사 격리도 그대로 적용돼야 하고, sync가 테넌트를 뭉개거나 권한을 우회하거나 시크릿을 공유 파일에 넣으면 안 됨. 설정이 커지면 `/harness-audit` 으로 컨텍스트 효율·품질 게이트·지속성·검색·보안을 점검하라고 함.

전체 진행은 이 한 줄로 정리됨.

**기억 → 맥락 → 정책 → 워커 → 리뷰 → 팀 기본값**

## 짚어야 할 것

**제품을 만든 쪽이 쓴 글임.** 본문에 "We built that shared layer with HQ"가 그대로 있음. 방법론과 제품 소개가 섞여 있고, 마지막 문단은 HQ를 써보라는 권유임. 다섯 가지 질문, 네 가지 속성, 세 층위 통제, 진단 표는 도구와 무관하게 이식되지만 `/newworker`·`/hq-sync`·`/harness-audit` 은 HQ에 묶임.

**별 58개짜리 저장소임.** 2026-04-21 생성. 성숙한 인프라로 보면 안 되는 규모이고, 팀 전체의 회사 기억을 얹을 대상으로 검토한다면 그 점을 먼저 감안해야 함.

**무엇이 오픈소스이고 무엇이 유료인지 이 글로는 안 갈림.** `hq-core` 는 MIT인데 hqforwork.com은 가격도 라이선스도 밝히지 않음. Slack·이메일 에이전트, 배포, 시크릿 관리 같은 기능이 어느 쪽에 속하는지 **확인하지 못했음.** 도입을 검토한다면 여기부터 물어봐야 함.

**"Main을 프로덕션처럼"이 실제로 강제되는지는 글에 없음.** 리뷰하고 sync하라는 절차는 있는데, 리뷰를 건너뛴 sync를 막는 기계적 장치가 있는지는 서술되지 않음. 저자 본인이 정의한 세 층위로 따지면 이건 정책이지 hook이 아님.

**시크릿 경계도 같은 문제임.** 워커 명세의 `Never` 와 정책 5번이 시크릿 노출을 금지하는데, 둘 다 모델에게 하는 요청임. hqforwork.com 쪽은 런타임 주입으로 키를 사용자에게 노출하지 않는다고 하는데, 그 경계가 sync된 공유 파일에도 적용되는지는 확인하지 못했음.
