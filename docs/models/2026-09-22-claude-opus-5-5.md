## 요약

2026-09-22 릴리스이고 Anthropic이 **"the first model in our new Claude 5.5 family"**라고 적음. 이 저장소에 걸리는 것이 넷임. 첫째, **공식 문서의 기본 권장이 Opus 5에서 Opus 5.5로 넘어감.** [Claude Fable 5.1](./2026-09-01-claude-fable-5-1.md) 문서가 인용한 "For most workloads, start with Claude Opus 5"는 더 이상 문서에 없음. 둘째, **effort 기본값만 `medium`임.** 다른 모든 모델은 `high`라서, `effort`를 안 적고 모델 ID만 갈아끼우면 한 칸 낮은 레벨로 돌게 됨. 셋째, **캐시 읽기 배수가 세 갈래로 갈림.** 기본 input 대비 Opus 5.5는 **0.05배**, Fable 5.1·Mythos 5.1은 0.025배, 나머지는 0.1배임. 넷째, **툴 호출 사이의 진행 상황 텍스트가 `text` 블록이 아니라 thinking 블록으로 옴.** 에러가 안 나고 화면만 조용해지는 종류의 변화라 제일 늦게 발견됨.

깨지는 API 변경이 넷인데 그중 셋(thinking 못 끔, 강제 툴 호출 400, thinking 블록이 대화에 묶임)은 Fable 5.1에서 이미 겪은 것과 같음. 즉 그 문서를 읽었으면 새로 배울 것은 **computer use 툴셋 교체** 하나임.

## 권장 기본이 바뀐 자리

Models overview 첫 문단이 이렇게 적음.

> "If you're unsure which model to use, start with Claude Opus 5.5 for most workloads. Use Claude Fable 5.1 for demanding reasoning and long-horizon agentic work, or when your evals on Claude Opus 5.5 at higher effort still fall short."

[Claude Fable 5.1](./2026-09-01-claude-fable-5-1.md)에 **"공식 문서가 대부분의 워크로드에는 Opus 5로 시작하라고 적음"**이라고 적어뒀는데, 그 문장이 가리키던 자리가 Opus 5.5로 옮겨감. Fable 5.1의 위치는 그대로임. 기본이 아니고, **Opus 5.5를 높은 effort로 돌려도 eval이 안 나올 때** 올라가는 모델임.

가격 차이도 그만큼 벌어짐. Fable 5.1이 input $10 / output $50이고 Opus 5.5가 $4 / $20이니 **2.5배** 차이임. 그 문서가 "캐시 읽기만 싼 것이지 전반적으로 싼 모델이 아니다"라고 적은 판단이 더 강해짐.

## effort 기본값이 한 칸 내려간 것의 의미

문서가 직접 적음.

> "Claude Opus 5.5 supports all five effort levels, and `medium` is the default (Claude Opus 5 and earlier Opus models default to `high`, so a request that omits `effort` runs one level lower than it did on Claude Opus 5)."

모델 ID만 바꾸고 `effort`를 안 적었다면, 같은 코드가 **더 얕게 생각하고 더 싸게 도는** 상태로 넘어간 것임. 품질이 떨어졌다고 느끼면 모델을 의심하기 전에 이 줄부터 봐야 함.

반대 방향의 함정도 같이 있음. **같은 레벨에서 Opus 5보다 턴당 더 많이 생각함.** `xhigh`와 `max`에서 특히 그렇다고 적힘. 즉 Opus 5에서 쓰던 값을 그대로 옮기면 턴이 길어지고 출력 토큰이 늘어남. 문서 권고는 셋임.

1. `max_tokens`를 넉넉히. thinking이 반환되지 않아도 `max_tokens`에 들어가므로 **thinking을 끄고 쓰던 값**이면 응답이 잘림. 에이전틱 코딩의 긴 턴에는 모델 최대인 **128,000**이 잘 들었다고 적음
2. `xhigh`·`max`는 품질 이득을 측정한 작업에만
3. 생각을 줄이려면 프롬프트로 지시하지 말고 **레벨을 내림**

Anthropic 자체 테스트 기준으로 **`medium`이 코딩·지식 작업 eval에서 Opus 5의 `high`와 같거나 그 이상**이고, 일부 코딩 eval에서는 `low`가 거기 근접한다고 적음. 자체 수치라 방향만 볼 것.

그리고 이건 [Prompt Caching In Agents](../agents/2026-07-22-prompt-caching-in-agents.md)의 8번 목록 5항과 직접 만남. **최상위 `effort` 값을 요청 사이에 바꾸면 캐시가 깨짐**은 그대로고, Opus 5.5는 per-message effort(베타 헤더 `mid-conversation-output-config-2026-07-01`)를 지원해서 그 경로로는 캐시가 살아남음. 지원 모델이 Fable 5.1·Mythos 5.1·Opus 5에서 **Opus 5.5까지 넷**으로 늘었음.

앞의 셋은 Fable 5.1과 같음. 넷째만 이 모델에서 새로 생긴 것이고, 옮길 때 툴 정의 교체로 끝나지 않음. 에이전트 루프를 멤버 `tool_use` 블록, 배치 액션, 결과의 `toolset_name`에 맞춰 고쳐야 한다고 문서가 적음.

**모델 간 thinking 블록 읽기 규칙**은 라우터를 짜는 쪽에서 따로 봐야 함.

| 이동 방향 | 앞선 추론이 넘어가나 |
|---|---|
| Opus 5 및 그 이전 Opus·Sonnet·Haiku → Opus 5.5 | 넘어감 |
| Opus 5.5 → Fable 5.1 · Mythos 5.1 (Claude API) | 넘어감 |
| Opus 5.5 → 위 둘 말고 다른 모델 | 안 넘어감 |
| Fable · Mythos → Opus 5.5 | 안 넘어감 |

읽을 수 없는 블록은 **조용히 떨어지고 과금도 안 됨.** 요청은 200으로 성공함. `thinking-binding-controls-2026-08-01` 헤더를 붙여야 `input_transformations`로 보고됨. [대규모 AI 코딩 비용 관리](../practices/2026-08-07-managing-ai-coding-costs.md)의 레버 2(동적 라우팅)를 실제로 붙일 거면, **싼 모델로 내려보내는 경로가 추론을 버리는 경로**라는 게 여기서 비용이 아니라 품질 항목으로 잡힘.

## 캐시 읽기 배수가 세 갈래가 됨

Models overview 각주가 이렇게 적음.

> "prompt cache reads cost 10% of the base input price (2.5% on Claude Fable 5.1 and Claude Mythos 5.1, 5% on Claude Opus 5.5)"

| 모델 | 캐시 읽기 (기본 input 대비) | 절대 가격 (MTok) |
|---|---|---|
| Claude Fable 5.1 · Mythos 5.1 | 0.025배 | $0.25 |
| **Claude Opus 5.5** | **0.05배** | **$0.20** |
| 그 밖의 현행 Claude 모델 | 0.1배 | 모델별 |

[Claude Fable 5.1](./2026-09-01-claude-fable-5-1.md)에 "0.025배는 이 모델만 예외"라고 적어뒀는데, 예외가 하나 더 생겨서 **이제 배수는 모델 속성으로 매번 찾아봐야 하는 값**임. 배수로 어느 쪽이 싼지 따지는 표를 들고 있다면 셋을 다 넣어 다시 계산해야 함.

절대 가격만 보면 Opus 5.5의 캐시 읽기($0.20)가 Fable 5.1($0.25)보다 낮음. 배수가 높은데 절대값이 낮은 이유는 기본 input이 $4 대 $10이기 때문임. **배수와 절대 가격이 반대 방향을 가리키는 구간**이라 어느 쪽으로 재는지 먼저 정해야 함.

[서버측 compaction](../practices/2026-09-20-claude-api-compaction.md)의 결론도 여기서 한 칸 움직임. 그 문서가 Fable 5.1을 근거로 "캐시 읽기가 싸면 일찍 compaction하는 게 손해일 수 있다"고 적었는데, Opus 5.5는 그 할인 폭이 절반이라 임계값 판단이 Fable 5.1만큼 늦게 잡히지 않음. 재는 것은 배수가 아니라 **자기 워크로드의 히트율**임.

## 코드를 안 바꿔도 드러나는 변화

### 진행 상황 텍스트가 thinking 블록으로 옴

이 모델에서 가장 조용히 깨지는 지점임. 툴 호출 사이에 모델이 쓰는 짧은 메모가 `text` 블록이 아니라 **progress-update thinking 블록**으로 오고, 기본 `thinking.display`가 `"omitted"`라 그 텍스트가 **빈 값**임.

> "an application that streams that text to its users as progress updates goes quiet between tool calls until it sets a `display` value that returns the text."

에러가 없음. `text` 블록만 렌더하는 클라이언트는 긴 에이전틱 턴 내내 화면이 멈춘 것처럼 보임. 받으려면 `display: "updates"`(베타 헤더 `thinking-display-updates-2026-08-18`)를 켜야 함.

문서가 붙인 하네스 처방 하나가 값어치 있음. `display: "updates"`를 켠 뒤 **사용자에게 읽을 것을 주지 않은 툴 호출 단계를 연속으로 세고**, 몇 번(예시는 다섯 번) 넘어가면 턴 한정 시스템 메시지(`clear_at: "next_user_message"`)로 짧은 리마인더를 덧붙이는 것임. Anthropic 자체 테스트에서 **긴 침묵 구간이 있는 작업 비율이 대략 절반으로 줄었고 비용에는 측정 가능한 변화가 없었음**이라고 적힘.

여기서 갈라 볼 것이 있음. 리마인더를 **덧붙여 두고 그대로 두기** 때문에 캐시가 계속 맞고 뒤의 thinking 블록도 유효함. [Claude Fable 5.1](./2026-09-01-claude-fable-5-1.md)이 400을 내는 패턴으로 지목한 **"요청마다 리마인더를 끼웠다가 다음 요청에서 빼는 것"**과 정확히 반대임. 같은 리마인더라도 넣고 빼면 에러고, 넣고 두면 지원 경로임.

### 무인 실행이 중간에 멈춤

긴 작업에서 Opus 5.5가 진행 상황을 보고하는데, 그중 일부가 **툴 호출 없이 텍스트로 턴을 끝냄**(`stop_reason: "end_turn"`). 무인 에이전트 루프가 그 턴을 작업 종료로 읽으면 거기서 멈춤.

문서 처방은 하네스 쪽임. 텍스트로 끝난 턴을 완료의 증거가 아니라 **보고**로 취급하고, 작업 항목을 모델이 갱신하는 체크리스트로 들고, 열린 항목이 남았는데 막힌 이유가 없으면 그 항목을 짚는 짧은 user 메시지를 보냄. 그리고 **같은 작업에서 자동 이어붙이기를 두세 번에서 끊으라**고 적음. 진짜 막힌 실행이 무한히 돌지 않게 하는 것임.

시스템 프롬프트로 조기 종료를 줄이는 문단도 문서가 예시로 주는데, 단서가 둘 붙음. **세션 첫 요청부터 넣어야 함**(중간에 넣으면 `system`이 바뀌어 앞선 thinking 블록이 무효가 됨), 그리고 사람이 옆에 있는 human-in-the-loop 애플리케이션에는 넣지 말라는 것임. 작업당 툴 호출과 출력 토큰이 다소 늘어난다고도 적음.

[자기개선 에이전트 루프의 7가지 규칙](../practices/2026-08-10-self-improving-agent-loops.md)의 문제의식이 여기 그대로 걸림. **"끝났다고 보고하는 것"과 "끝난 것"을 가르는 판정이 루프 바깥에 있어야 함.** 문서가 제시한 대안 중 하나도 그 형태임. 완료 조건을 미리 적어두고 **더 작은 별도 모델**이 매 턴 끝에서 대조하게 하는 것.

### 그 밖

- **시간 신호에 민감함.** 멀티에이전트 하네스에서 매 메시지 끝에 `elapsed 340s / 1200s` 같은 경과·예산 줄을 붙이면 모델이 그 안에 맞춰 일을 배치함. Anthropic 평가에서 예산을 준 팀이 단일 에이전트와 답 품질은 비슷하면서 상당히 일찍 끝냈다고 적음. **예산은 권고일 뿐 한계선에서 멈추지 않으므로** 하드 스톱이 필요하면 자기 타임아웃을 따로 둘 것
- **멀티앱 워크플로에서 먼저 둘러보게 해야 함.** 작업이 명시하지 않은 곳(옛 메일 스레드의 정책, 다른 시트 탭의 규칙)에 근거가 있을 때, 행동 전에 넓게 탐색하라는 한 문장을 시스템 프롬프트에 넣으면 정답률이 눈에 띄게 올랐다고 적음. 대가는 툴 호출과 토큰이 조금 늘어나는 것. ⚠️ 문서가 단서를 붙임. **찾은 것을 근거로 행동하게 하는 지시이므로, 검색 대상 레코드에 신뢰할 수 없는 콘텐츠가 섞이면 안 됨**
- **차트·다이어그램·스크린샷 읽기가 나아짐.** 자체 테스트 기준으로 **최저 effort에서도 Opus 5의 최고 effort보다 조밀한 차트의 값을 정확히 읽었고** 출력 토큰은 일부만 썼다고 적음. 이전 모델용으로 만든 비전 우회책이 지금도 필요한지 다시 재보라는 것이 문서 권고임
- **safeguard 분류기가 늘어남.** 생물학(Fable 5.1과 동일, Opus 5에서 오면 새것)과 `reasoning_extraction`이 추가됨. **추론을 응답 텍스트에 그대로 써내라고 밀어붙이는 프롬프트가 거절될 수 있음.** 거절은 200에 `stop_reason: "refusal"`로 오고, `reasoning_extraction` 거절만은 서버측 폴백이 재시도하지 않고 그대로 돌려줌

### 붙여넣은 텍스트에 태그를 치는 것

간접 프롬프트 인젝션 내성이 **이전 Opus 모델 중 가장 낫다**고 적으면서, 사용자가 다른 데서 복사해 온 텍스트에 대해서는 조건을 붙임. **어디까지가 사용자 본인의 말이고 어디부터가 붙여넣은 것인지 표시해야** 그 내성이 나온다는 것임. 각 붙여넣기 블록을 여는 태그와 닫는 태그로 감싸고, 둘에 애플리케이션이 만든 **같은 짧은 랜덤 ID**를 달고, 태그를 각각 제 줄에 둠. 그리고 그 태그의 의미를 시스템 프롬프트에 적음.

문서 자신이 한계를 적어 둠. **태그는 평문이라 흉내낼 수 있고**, 이것은 다른 인젝션 방어와 함께 쓰는 가드레일 하나라는 것. 그리고 모델이 때때로 조금 더 조심스러워지므로 자기 작업에서 영향을 재라고 함.

[사람이 에이전트 명령 승인에서 위협 3건 중 1건을 놓친다](../security/2026-08-05-agent-approval-miss-rates.md)의 결론과 같은 방향임. 모델의 판정 정확도를 올리는 쪽이 아니라 **판정해야 할 입력의 경계를 먼저 그어주는 쪽**이 싸고 확실함.

## Fast mode

research preview이고 `speed: "fast"` + 베타 헤더 `fast-mode-2026-02-01`로 켬. 지원 모델은 **Opus 5.5, Opus 5, Opus 4.8** 셋이고, **Claude API 한정**임(Claude Managed Agents 포함). Bedrock, Claude Platform on AWS, Google Cloud, Microsoft Foundry에서는 안 됨.

| 항목 | 내용 |
|---|---|
| 효과 | 출력 토큰 초당 처리량(OTPS) **최대 2.5배**. **TTFT는 아님** |
| 모델 | 같은 가중치·같은 동작. 추론 구성만 빠른 것 |
| 가격 | Opus 5.5 **input $8 / output $40** (표준의 2배). Opus 5·4.8은 $10 / $50 |
| 접근 | 계정 매니저에 요청하거나 대기자 명단 |
| 레이트 리밋 | 표준 Opus와 **별도 한도**. 초과 시 429에 `retry-after` |
| 캐시 | **fast와 standard는 캐시 prefix를 공유하지 않음.** 속도를 갈아타면 미스 |
| 안 되는 조합 | Batch API, Priority Tier |

마지막 두 줄이 실무에서 걸림. 429가 났을 때 표준 속도로 폴백하는 코드는 **그 순간 캐시 미스를 한 번 먹는다**는 뜻이고, [Prompt Caching In Agents](../agents/2026-07-22-prompt-caching-in-agents.md)가 정리한 대로 그 비용은 대화 길이에 비례함. 긴 세션에서 폴백을 자동으로 돌리면 절약하려던 것보다 더 낼 수 있음.

`usage.speed`로 어느 속도로 돌았는지 확인할 수 있음. Opus 4.6은 예외적으로 에러 없이 표준 속도로 내려가고 `usage.speed`가 `"standard"`로 옴.

## 거절도 과금 대상이 넓어짐

같은 주 릴리스 노트(2026-09-24) 항목이라 여기 붙임. 출력이 나오기 전에 도착한 거절 중 `stop_details.category`가 **`"bio"`, `"frontier_llm"`, `"reasoning_extraction"`**인 것이 이제 과금됨. 스트림 중간 거절은 원래 과금 대상이었음. 그 밖의 카테고리에서 출력 전 거절은 여전히 무료이고 폴백 크레딧은 그대로임. 전 플랫폼 적용임.

Opus 5.5에서 `reasoning_extraction`이 새로 생긴 카테고리라는 것과 겹쳐 읽어야 함. **추론을 응답에 써내라고 시키는 오래된 프롬프트가 남아 있으면, 거절되고 과금까지 되는 조합**이 됨.

## 짚어야 할 것

- **이 문서는 공식 문서와 발표만 읽었고 직접 써보지 않았음.** 동작 변화 항목들은 Anthropic이 자기 테스트로 적은 것임
- **벤치마크와 비용 수치는 전부 자체 발표임.** GDPval-AA v2.1의 측정 조건과 Elo 산출 방식은 발표에서 확인하지 못했고, "40% 저렴"은 기본 설정과 전형적 워크로드를 전제로 한 값임. effort를 올려 쓰면 성립하지 않음
- **"Claude 5.5 family의 첫 모델"이라고 적혀 있으니 뒤에 더 나옴.** 지금 시점의 비교표는 곧 낡음
- **마이그레이션 가이드 본문은 열지 않았음.** 각 깨지는 변경의 before/after 코드는 그쪽에 있고, 이 문서는 무엇이 깨지는지와 왜까지임
- **Claude Code나 claude.ai에서 이 모델이 어떻게 노출되는지, 구독 플랜 한도는 확인하지 않았음.** 위 내용은 전부 Claude API 기준임
- **시스템 카드는 이번에 찾지 못했음.** 안전 평가 쪽 서술은 발표 문구와 프롬프팅 문서의 safeguard 절까지만 확인함
- 거절 과금 확대 항목의 `frontier_llm` 카테고리가 무엇을 가리키는지는 **릴리스 노트가 이름만 적고 설명하지 않음.** 확인하지 못했음
