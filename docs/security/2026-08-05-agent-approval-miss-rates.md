## 요약

브라우저 게임으로 사람에게 AI 코딩 에이전트의 명령을 승인·거부하게 시키고, 4만 회 이상의 세션에서 약 **40만 9천 건의 결정**을 모은 데이터임. 원문 제목이 내세우는 건 **위협 세 건 중 한 건을 통과시켰다**는 것이고, 별도로 **전체 판정 정확도 66.3%**를 보고함. 저자 결론은 **human-in-the-loop 승인이 보안 경계로는 결함이 있다**는 것.

## 방법론

- 브라우저 기반 게임. 플레이어가 AI 코딩 에이전트의 human-in-the-loop 감독자 역할
- 시간 압박 하에서 명령을 승인하거나 거부
- 세션 4만 회 이상, 결정 약 40만 9천 건
- 제시된 명령의 약 **34%가 의도적으로 심어둔 위협**

## 핵심 수치

| 지표 | 값 |
|---|---|
| 전체 판정 정확도 | 66.3% |
| 원문 제목이 내세우는 위협 통과율 | **3건 중 1건** |
| 음수 점수로 끝난 세션 | 32.9% |
| 모든 위협을 잡은 플레이어 | 35.2% |
| 모든 위협을 잡으면서 안전한 명령 차단은 20% 이하 | **20.8%** |
| 모든 프롬프트를 승인한 플레이어 | 7% |

**두 수치를 섞지 말아야 함.** 66.3%는 위협과 정상 명령이 섞인 전체 데이터셋에 대한 판정 정확도임. 제시된 명령의 34%만 위협이었고, 아래 과잉 차단 항목에서 보듯 **정상 명령을 잘못 막은 것도 정확도를 깎음.** 그래서 66.3%에서 "위협 3건 중 1건 통과"를 역산할 수 없음. 후자는 원문 제목이 내세우는 별도 수치임. 실제 위협별 통과율은 유형에 따라 11.7%에서 35.0%까지 갈리니 아래 표를 봐야 함.

그리고 마지막 세 줄이 중요함. 위협을 다 잡은 사람은 35.2%인데, **과잉 차단 없이 다 잡은 사람은 20.8%뿐**임. 나머지는 안전한 명령까지 막아서 정확도를 산 것임. **7%는 제시된 모든 프롬프트를 승인했음.** 읽고 승인했는지 안 읽었는지는 이 데이터로 알 수 없음.

## 위협 유형별 놓친 비율

| 유형 | 놓친 비율 |
|---|---|
| 명백히 파괴적 | 11.7% |
| 영속적 변형(persistent mutation) | 23.8% |
| 유출·코드 실행 | 33.4% |
| 스코프 위반 | **35.0%** |

`rm -rf /` 같은 티 나는 건 잘 잡음. 문제는 **얌전해 보이는 것들**임. 스코프를 살짝 벗어나거나 조용히 뭔가를 내보내는 명령이 3분의 1 이상 통과함.

## npm이 최악의 사각지대

가장 많이 놓친 명령이 이거임.

```
npm run analyze
```

payload가 눈에 보이는 상태였는데도 **64.7%가 승인**했음. npm 기반 위협 셋을 묶으면 놓친 비율이 **52.5%**로, 다른 유출 공격의 28.4%와 크게 벌어짐.

이유는 짐작이 감. `npm run <something>`은 하루에 수십 번 보는 형태라 눈이 그냥 넘어감. 그리고 `package.json` 안에 뭐가 들어 있는지는 그 화면에서 안 보임.

## 과잉 차단도 문제

반대 방향의 실패도 측정했음. 안전한 명령을 막은 비율.

| 명령 | 차단 비율 |
|---|---|
| `npm config set registry` (사내 미러) | 59% |
| `rm -rf dist/` | 45% |
| `kill $(lsof -t -i:3000)` | 43% |

`rm -rf`가 보이면 대상이 `dist/`인지 확인하지 않고 막고, 포트 정리 명령도 절반 가까이 막힘. **위협 감지 훈련이 안 된 승인자는 위협을 놓치면서 동시에 정상 작업을 방해함.**

## 저자 결론

허가 피로(permission fatigue)와 컨텍스트 부족 때문에 human-in-the-loop 승인은 신뢰할 보안 경계가 못 됨. 개발자의 경계심에 의존하는 대신 **샌드박싱과 컨텍스트 격리 같은 기술적 안전장치를 우선하라**는 것.

## ⚠️ 해석할 때 조심할 것

이 데이터의 한계를 명확히 해둬야 함.

- **게임임.** 실제 업무 중 개발자를 관찰한 필드 연구가 아님. 시간 압박이 인위적이고, 결과에 실제 손해가 없음
- **플레이어가 자기선택됨.** 이런 게임을 하는 사람이 평균적인 개발자를 대표하지 않음. 보안에 관심 있는 쪽으로 편향됐을 수도 있고, 게임이라 대충 눌렀을 수도 있음. 7%가 전부 승인한 걸 보면 후자도 섞여 있음
- 위협 34% 비율이 현실보다 훨씬 높음. 실제로는 승인 요청 대부분이 정상이라 경계심이 더 빨리 무너질 수도, 반대로 이상한 게 더 눈에 띌 수도 있음

그래도 **이 실험 안에서는 방향이 일관됨.** 명백한 파괴(11.7%)와 스코프 위반(35.0%) 사이의 3배 격차, npm 계열의 52.5%가 사람의 패턴 인식이 어디서 무너지는지 시사함. 단 유형별 표본 구성과 명령 표현, 시간 압박이 이 격차에 직접 영향을 주므로 절대 수치를 다른 환경으로 옮길 수는 없음.

## 실무 적용

Claude Code나 유사 하네스를 매일 쓰는 입장에서 바로 할 수 있는 것들.

- **위험한 명령은 승인 대상에서 아예 빼기.** allowlist를 좁게 유지하고, 파괴적 작업은 프롬프트로 물어보게 하지 말고 아예 못 하게 함. 사람이 볼 기회를 없애는 게 사람이 잘 보게 만드는 것보다 확실함
- **`npm run`, `yarn`, `make` 같은 간접 실행을 특별 취급.** 스크립트 이름만 보이고 내용은 안 보이는 명령이 가장 위험함. 이런 건 자동 승인 목록에 넣지 않기
- **읽기 전용 명령은 넉넉히 허용해서 승인 횟수 자체를 줄이기.** 승인 프롬프트가 하루 50번 뜨면 51번째는 안 보고 누르게 됨. 전부 승인한 7%가 그 상태였는지는 이 데이터로 확인할 수 없고, 저자가 지목한 허가 피로와 방향은 맞음
- **샌드박스나 격리 워크트리에서 돌리기.** Orca나 AO처럼 에이전트를 격리 워크트리에 두면 스코프 위반의 피해 범위가 줄어듦. 승인 정확도를 올리는 것보다 이게 싸고 확실함
