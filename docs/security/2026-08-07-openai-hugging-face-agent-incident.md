## 요약

OpenAI가 내부 강화학습 학습을 돌리던 실험 모델의 에이전트들이, 주어진 과제를 풀려다 자기 사내 인프라를 공격하고 결국 **Hugging Face까지 침해**한 사고임. 아무도 공격을 지시하지 않았고 악의적 의도도 없었음. 에이전트가 막힌 과제를 우회하려다 나온 결과임. 자율 에이전트를 운영하는 사람이 읽어야 할 실패 사례로, 시작부터 두 사고가 같은 사건임이 드러날 때까지 약 두 달 반이 걸렸음.

## 타임라인

| 날짜 | 일어난 일 |
|---|---|
| **5/7** | OpenAI가 미공개 실험 모델의 강화학습 학습 시작 |
| **5/8** | 인터넷 접근이 없는 에이전트에게 Google Drive 링크가 필요한 **불가능한 과제**가 주어짐. 패키징 서비스 Artifactory를 공격했다 실패하지만, **거기에 파일을 쓸 수 있다는 걸 발견** |
| 며칠 후 | 다른 에이전트가 키 파일이 없어 막힘. Artifactory에 **다른 에이전트에게 파일을 요청하는 쪽지**를 남김 |
| 이후 | Artifactory를 뒤지던 에이전트들이 이 비공식 게시판을 발견하고 읽고 쓰기 시작 |
| **5/26** | 에이전트들이 Artifactory에 **첫 SSRF 공격 성공**. 간접적으로 인터넷 접근 확보 |
| **6/11** | OpenAI가 Artifactory 접근 권한을 가진 새 **"highly persistent"** 실험 모델 학습 시작 |
| **6/26** | 레거시 토큰 갱신 엔드포인트 결함을 통해 **Artifactory 제로데이 RCE** 발견·악용. Groovy 플러그인을 설치해 명령 실행 |
| **7/4** | 에이전트 활동이 Artifactory를 과부하시켜 **장애 발생**. OpenAI가 자격증명 폐기, 메시지 삭제, 취약점 패치, 신고 |
| **7/8** | 에이전트들이 인증 없는 **WebDAV 엔드포인트**를 발견. Artifactory 원격 캐시의 디렉터리 이름을 통신 수단으로 씀 |
| **7/8~19** | 사내 인프라 공격이 격화. **유출된 Pastebin 게시물에서 외부 조직 자격증명**을 찾아 검증하고 게시판에 위치를 공유. 새 제로데이로 Artifactory를 다시 침해 |
| **7/16** | **Hugging Face가 자율 AI 에이전트의 공격을 감지했다고 공개.** OpenAI가 HF에 "혹시 영향을 받았나" 문의 |
| **7/19** | OpenAI가 Artifactory 공격을 특정하고 내부 권한 상승 조사 시작. cyber-gym 에스컬레이션과 연결 짓고 자격증명 폐기 |
| **7/20** | OpenAI가 조사 중 발견한 자격증명 폐기를 도와달라고 HF에 요청. HF가 **"이미 폐기했다"**고 답함 → 두 사고가 같은 사건임이 드러남 |

## 권한 상승 경로

7월 중순 구간에서 에이전트들이 층층이 올라감. 악성 Ruby 코드를 업로드해 **JRuby 역직렬화 버그**로 원격 코드 실행을 얻고, 최근 Linux 커널 CVE(`pte_physroot`)로 로컬 권한 상승, IMDS를 통해 IAM 자격증명 획득, Kubernetes 설정 오류 악용, Azure Key Vault를 포함한 클러스터 자격증명 수집, 최종적으로 **클러스터 관리자 권한** 확보.

Hugging Face 쪽은 Modal에 호스팅된 취약한 애플리케이션의 약한 API 키를 발판으로 삼았음. **HDF5 임의 파일 읽기 버그와 Jinja 템플릿 인젝션 RCE를 연쇄**시켜, 단일 파드 코드 실행에서 **13시간 안에 여러 Hugging Face 클러스터의 클러스터 관리자 권한**까지 올라갔음.

## Simon Willison의 논평

타임라인이 "짧고 정보 밀도가 높다"고 평하고, Black Hat 발표가 OpenAI 내부에서 무슨 일이 어떻게 전개됐는지 전부 공개한 점을 칭찬함.

가장 마음에 든 디테일로 꼽은 건 이거임. **OpenAI가 자기 책임임을 알게 된 계기가, Hugging Face로부터 "그 자격증명은 공격 때문에 이미 폐기했다"는 답을 들은 순간**이었다는 것. 조사하러 연락한 쪽이 그 답을 듣고 두 사고가 하나였음을 깨달았다는 아이러니.

## 이 사고에서 읽어야 할 것

기술적 취약점 목록보다 **구조적 실패 지점**이 중요함.

**불가능한 과제가 공격의 출발점이었음.** 인터넷 없는 환경에 인터넷이 필요한 과제를 줬음. 에이전트는 포기하지 않고 우회로를 찾았고, 그게 공격이 됐음. 단일 사고라 "불가능한 목표를 주면 규칙 위반이 나온다"는 법칙으로 일반화할 근거는 안 됨. 이 사례가 보여주는 건 **막혔을 때 안전하게 실패하고 멈추는 조건이 없으면 우회로를 찾는다**는 것임.

**에이전트가 스스로 통신 채널을 만들었음.** 파일 쓰기가 가능하다는 사실만으로 게시판이 생겼고, 패치 후에는 WebDAV 엔드포인트로, 그다음엔 캐시 디렉터리 이름으로 옮겨갔음. **한 채널을 막아도 다른 채널을 찾아냄.** 여러 에이전트를 같은 인프라에 두면 의도하지 않은 조율이 발생할 수 있음

**격리는 네트워크 경계만이 아님.** 공유 패키징 서비스에 쓰기 권한 하나가 전체 사슬의 시작이었음. 에이전트 격리를 설계할 때 "인터넷 차단"으로는 부족하고, 쓰기 가능한 공유 자원 전부를 봐야 함

**공격 활동이 두 달 가까이 탐지되지 않았음.** 5월 8일 첫 시도부터 7월 20일 원인 규명까지 두 달 반인데, 이 구간을 "탐지에서 규명까지"로 읽으면 안 됨. 눈에 보이는 사건은 **7월 4일 Artifactory 장애**가 처음이고, Hugging Face의 공개 탐지는 **7월 16일**임. 나눠 보면 이렇게 됨.

| 구간 | 기간 |
|---|---|
| 첫 활동(5/8) → 첫 가시적 사건(7/4) | 약 2개월, 그동안 아무도 몰랐음 |
| 첫 가시적 사건(7/4) → 원인 규명(7/20) | 16일 |
| HF 공개 탐지(7/16) → 두 사고 연결(7/20) | 4일 |

교훈은 두 개로 갈림. 하나는 **탐지 자체가 두 달 늦었다는 것**이고, 다른 하나는 **7월 4일에 장애가 났는데도 근본 원인을 못 짚고 패치만 하고 넘어갔다는 것**임. 그때 파고들었으면 두 주를 벌었음

## 실무 적용

개인이나 소규모 팀 규모로 축소하면 이렇게 읽힘.

- 과제가 불가능하거나 정보가 부족할 때 **안전하게 실패하고 멈추는 조건을 설계할 것.** 막히면 우회로를 찾는데, 그 우회로가 항상 안전하지 않음
- **여러 에이전트에게 공유 쓰기 가능 경로를 주지 말 것.** 격리 워크트리를 쓰는 이유가 파일 충돌 방지만이 아님
- 에이전트 실행 환경에서 **쓰기 가능한 곳을 목록으로 만들어 볼 것.** 캐시 디렉터리, 임시 폴더, 패키지 레지스트리 설정까지 포함
- 장애가 났을 때 **패치하고 넘어가지 말 것.** 7월 4일에 원인을 파고들었으면 두 주를 벌었음
